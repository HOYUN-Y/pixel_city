isometric.nyc가 먼저고, Isopolis가 여기서 영감을 받아 SF로 다시 만든 것이다.
HN에서는 두 프로젝트의 비용·수작업 격차를 "AI 발전의 비공식 벤치마크"로 언급한다.

Isopolis는 드라마 *Silicon Valley* 오프닝 크레딧 재현도 의도했다.
제공 기능: 583개 장소 중 177개 표시, 가이드 투어 4개, 장소 검색, 앰비언트 오디오.

## 2. Isopolis 파이프라인 (개발 노트 기준)

### 2.1 3D 렌더 확보 — 입력 이미지 만들기

- **소스**: Google Photorealistic 3D Tiles.
  LIDAR도 검토했으나 **텍스처가 있는 쪽이 모델 학습에 유리**하다고 판단해 탈락.
- **렌더러**: three.js + NASA 3D Tiles Renderer를 **Playwright 헤드리스**로 구동, 병렬 처리.
- **카메라**: 고정 ENU(East-North-Up) 로컬 접선 평면 좌표계 + **직교(orthographic) 카메라**,
  방위각 22.5° / 고도각 30° (= SimCity 뷰).
- **산출**: 440개 블록 × 1024².
- **좌표 → 픽셀 변환**
  ```
  u = (e·cos α − n·sin α) / s
  v = −[(e·sin α + n·cos α)·sin φ + h·cos φ] / s
  ```
  오차가 누적되지만 도시 규모에서는 무시 가능한 수준이라고 기술.
- **병목**: Google TOS 레이트 제한. 워커 최적화로 블록당 **3분 → 20초**.

> 시사점: 전체 도시를 **하나의 전역 프레임**에 고정한 것이 핵심.
> 블록별로 카메라를 따로 잡으면 기하 연속성부터 깨진다.

### 2.2 학습 데이터 구성

- **정답(ground truth)**: Google **Nano Banana**로 지브리풍 픽셀아트 생성.
  레퍼런스 이미지 8장으로 스타일을 고정한 뒤 60쌍 / 100쌍 두 세트 제작. **총 ~$4**.
- **색상 정규화**: 입력(렌더)과 출력(픽셀아트)을 채널별 평균·표준편차로 정규화.
  물과 식생은 마스킹해 **건축 환경만 학습**하도록 유도.
- **물 처리 (최대 난관)**: 직교 렌더의 개방 수역은 텍스처가 없어 모델이 구조를 환각한다.
  - HSV 휴리스틱으로 물 마스크 자동 생성
  - 얕은 물(색조 190–197, 채도 0.34–0.38)과 그림자가 겹쳐서 **명도 조건을 추가**해 분리
  - 체커보드 입력으로 학습 데이터 준비, 후처리에서 수동 보정
- **infill 증강**: 학습 이미지를 4분할하고 "어느 사분면이 주어지고 어느 쪽을 생성할지"를
  **15가지 패턴**으로 확장 → 100쌍 × 15 = **1,515 샘플**.
  이게 인접 영역과의 연속성을 강제하는 장치다.
  추론 시 기본 작업은 `1010` 패턴(좌우 열이 주어지고 상하 열을 생성).

### 2.3 파인튜닝

- **베이스**: Qwen-Image-Edit-2511 (20B, Apache 2.0, bf16).
  이미지→이미지 번역이 되는 오픈 웨이트 중 최고 품질로 평가.
- **LoRA**: 베이스 완전 동결, 각 어텐션 프로젝션에 저차 잔차 추가.
  - r = 16, B 행렬 0 초기화
  - 학습 파라미터 **~55M (전체의 0.28%)**, LoRA 산출물 **~200MB** (베이스 40GB 대비)
- **환경**: Modal 서버리스 **H100** (시간당 ~$4).
  배치 1 / 그래디언트 축적 4 / bf16, 실행당 2~3시간, **$10~15 × 2회**.
- **트레이너**: 직접 작성한 **500줄 HF 트레이너** (diffusers + peft + accelerate).
- **평가**: 100스텝마다 검증 손실, 250스텝마다 미리보기 그리드.
- **추론 샘플링**: CFG 4.0, Euler 24스텝.
- **선택**: 100쌍 모델 > 60쌍 모델.

### 2.4 추론 — 연속성 확보 전략

블록을 독립적으로 생성하면 **기하는 연속인데 스타일·팔레트가 튄다**.

**Overlap plan (슬라이딩 윈도우)**
1. 첫 이미지는 패턴 `0000`(전체 생성)
2. 이후 반 이미지씩 밀면서 패턴 `1010`으로 생성 — 기존 열을 컨텍스트로 새 열만 생성
3. 이 방식이 **학습 목표와 정확히 일치**하는 게 포인트

결과: 440블록 → **1,519회 생성 / 67 웨이브**.

단점:
- DAG 의존 구조라 직렬화되어 **매우 느리다**
- 인접 윈도우가 충돌하는 **이음새(seam) 불연속은 아직 미해결**

**물 관련 OOD**: 대부분이 바다인 윈도우는 분포 밖이라 모델이 물 위에 도시를 그렸다.
→ 물 비율이 임계값을 넘으면 **생성을 건너뛰고 물 스탬프로 대체**.

### 2.5 검수 & 타일링

- 생성된 **1,606개 사분면을 저자가 직접 육안 검토(~1시간)**, 약 200개(8.3%)를 재생성 대상 표시.
- 재생성은 **검증된 인접 사분면을 컨텍스트로** 문제 사분면만 다시 생성 → 반복.
- **금문교**: 극단적 OOD. 결국 Nano Banana 수동 생성분 50%를 합성해 해결.
- **물 타일링**: 100% 물 영역은 단일 물 타일, 혼합 영역은 마스크 기반 스탬핑으로 겹침.
- **타일 피라미드**: 2,630 사분면(생성 1,606 + 물 스탬프 1,024)
  → 9단계 (Level 0이 사분면, 상위 레벨은 2×2 자식을 BOX 다운샘플)
  → **총 3,570 타일 / 287MB**.

### 2.6 프론트엔드

- **맵 라이브러리 없음. 커스텀 Canvas 엔진.**
  Mercator가 아니라 로컬 ENU **dimetric 투영**을 쓰기 때문.
- CARTO 다크 베이스맵 타일을 같은 dimetric 프레임으로 왜곡해 **알파 45%**로 깔아 맥락 제공.
- 픽셀아트 타일 피라미드는 단일 패스 렌더링.
- 데이터 레이어: GeoJSON(`[lon, lat, h]` → 맵 픽셀 투영) — 간판, 회사 로고, 스프라이트,
  동네 다각형, 투어 경로(OSM 기반).
- **앱 상태를 URL 해시에 저장** (`#@lat,lon,scale/…`) → 모든 뷰가 공유 가능한 링크가 됨.
- 오디오: Silicon Valley 오프닝 음악 + 앰비언트.
- 호스팅: **S3 + CloudFront** 정적.
- 폰트: Press Start 2P, VT323.

### 2.8 코딩 에이전트 기여

저자 명시: Claude Opus 5 ~30% / Claude Fable 5 ~40% / GPT-5.6-Sol ~30%.
"이들 없이는 불가능했고 혼자였다면 10배 오래 걸렸을 것."
저자의 역할은 **메타 프로그래밍과 미적 판단**이었다고 기술.

## 3. 문제 → 해결 대응표

| 문제 | 원인 | 해결 |
|---|---|---|
| 렌더링 속도 | Google TOS 레이트 제한 | 워커 병렬화 최적화 (3분 → 20초) |
| 색상 드리프트 | 블록 독립 생성 시 팔레트 불일치 | 채널별 정규화 + HSV 변환 |
| 물 환각 | 직교 렌더의 수면에 텍스처가 없음 | 마스크 기반 입력 + 후처리 스탬핑 |
| 얕은 물 vs 그림자 혼동 | HSV 채도 범위가 겹침 | 명도(V) 조건 추가 |
| 블록 간 스타일 불연속 | 독립 생성 | Overlap plan (슬라이딩 윈도우, `1010` 패턴) |
| 물 위에 도시 생성 | 바다 윈도우가 OOD | 물 비율 임계값 초과 시 생성 스킵 |
| 금문교 붕괴 | 극단적 OOD | Nano Banana 수동 생성분 합성 |
| **이음새 불연속** | 인접 윈도우 충돌 | **미해결** |
| **자동 품질 검사 부재** | 신뢰할 QA 모델 없음 | **미해결 — 수동 검수로 대응** |

## 4. 커뮤니티 반응 (Hacker News)

- **고도 표현 없음**: 아이소메트릭인데 지형 높낮이가 시각적으로 안 드러나 SimCity 2000 같은
  입체감이 부족하다는 지적.
- **물 오인식 사례**: 텐더로인의 없는 인공 연못, 부에나비스타 공원 동쪽의 없는 호수 등.
- **"픽셀아트가 아니다"**: 흐릿하고 선이 흔들려 진짜 픽셀아트가 아니라 생성 이미지의
  부산물이라는 비판. 수작업 픽셀아트 대비 "영혼이 없다"는 의견.
- **저작권**: Google Earth 사진으로 학습된 확산 모델의 산출물을 스타일화해 쓰는 것이
  공정이용인지 — 결론 없는 그레이존. "Google도 남의 사진으로 학습했다"는 반론.
- **반복 지적된 진짜 병목**: 믿을 만한 **자동 품질 검사 모델이 없어서 수동 검수가 안 줄어든다.**
  isometric.nyc 저자가 200시간을 쓴 이유이며, "AI 이점이 명확한가"라는 회의의 근거.
- 긍정 평가: "위성 지도보다 도시 이해가 명확하다", "탐험이 즐겁다", "SimCity 2000 분위기".

## 5. `pixel_city`에 주는 시사점

1. **전역 고정 프레임이 1순위 설계 결정.** ENU + 직교 카메라 + 고정 방위/고도.
   여기가 어긋나면 뒤의 모든 연속성 장치가 무의미해진다.
2. **연속성은 학습 목표에 넣어야 한다.** infill 15패턴 증강 + 추론 시 동일 패턴 사용.
   후처리 블렌딩으로 때우는 접근은 저자도 실패했다.
3. **물/식생 같은 텍스처 없는 영역은 생성이 아니라 마스크·스탬프로 처리한다.**
   모델에 맡기면 환각한다.
4. **비용은 학습이 아니라 생성량과 수동 검수가 결정한다.**
   SF $25~35 vs NYC $600, 검수 1시간 vs 200시간. 범위를 좁히면 급격히 싸진다.
5. **뷰어는 기성 맵 라이브러리를 못 쓴다.** dimetric 투영이라 Leaflet/MapLibre가 안 맞음.
   커스텀 Canvas + 타일 피라미드 + URL 해시 상태가 검증된 조합.
6. **미해결 영역이 곧 차별화 지점**: 이음새 블렌딩, 자동 QA, 고도 표현.
