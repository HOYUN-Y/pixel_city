## 1. 한 줄 정의

**서울 도심 관광축을 AI로 생성한 아이소메트릭 픽셀아트 지도로 재현하고,
그 위에 공공 관광·공간 데이터를 레이어로 얹은 인터랙티브 관광 지도.**

- **출품 목적**: 공모전 (주제 = 공간데이터 + AI). **비영리.**
- **성격**: **프로토타입.** 전체 서비스가 아니라 "이 방식이 된다"를 보여주는 것이 목표다.
- **마감**: **2026-09-18** (제8회 공간정보 활용·아이디어 경진대회, GeoAI 혁신 아이디어 분야) → §8
- **레퍼런스**: Isopolis(SF) — 검증된 파이프라인을 서울에 이식하고, **관광 데이터 결합**으로 차별화.

## 2. 왜 이 조합인가

공모전 주제가 "공간데이터 + AI"인데, 대부분의 출품작은 **공간데이터를 분석**하는 쪽으로 간다.
이 프로젝트는 **공간데이터로 새로운 시각적 자산을 생성**하고, 그 위에 다시 공간데이터를 얹는다.

| 심사 축 | 이 프로젝트의 대응 |
|---|---|
| 공간데이터 활용도 | V-World 3D 건물·항공영상·DEM을 **생성 모델의 입력**으로 사용 (단순 조회가 아님) |
| AI 활용도 | 확산 모델 LoRA 파인튜닝 — 프롬프트 호출이 아니라 **직접 학습** |
| 독창성 | 국내에 동일 사례 없음. 해외(Isopolis/isometric.nyc)도 관광 데이터 결합은 안 함 |
| 완성도 | 범위를 좁혀 "끝까지 완성된 것"을 보여줌 |
| 실용성 | 관광 코스 추천 = 실제 사용 시나리오 존재 |

## 3. 대상 범위

**서울 도심 관광축, 약 6~8 km².**

우선 후보: **경복궁 — 광화문 — 북촌 — 인사동 — 종로 — 명동 — 남산** 축.
(여의도·강남은 픽셀아트로 그림은 되지만 관광 서사가 약해 후순위)

### 왜 이 범위인가

| | SF (Isopolis) | 서울 전역 | **본 프로젝트** |
|---|---|---|---|
| 면적 | 121 km² | 605 km² | **~7 km²** |
| 렌더 블록 | 440 | ~2,200 (추정) | **~40 (추정)** |
| 생성 횟수 | 1,519 | ~7,500 (추정) | **~150 (추정)** |
| 검수 사분면 | 1,606 (~1시간) | ~8,000 | **~160 (하루 이내)** |
| 생성 비용 | $25~35 | 추정 $150+ | **$30~50** |

> ⚠️ 서울 전역·자치구 단위 수치는 SF 기준을 면적 비례로 환산한 **추정치**다. 실측 아님.

**좁힌 이유**: isometric.nyc가 200시간 수동 검수에 갈린 사례가 있다.
공모전은 마감이 고정이므로 **"넓지만 미완성"보다 "좁지만 완성"**이 유리하다.
범위는 나중에 넓힐 수 있지만, 미완성은 출품 시점에 되돌릴 수 없다.

## 4. 데이터 소스 매핑

### 4-A. 픽셀 지도 생성용 (파이프라인 입력)

| 데이터 | 출처 | 용도 | 확인 필요 |
|---|---|---|---|
| 3D 건물 모델 (LOD3~4, 실사 텍스처) | **V-World 3D 데이터 API** | 직교 렌더 → 모델 입력 | 서울 도심 LOD3~4 실제 커버리지 |
| 항공영상 25cm | V-World | 텍스처 보강 | |
| 수치표고모형 DEM 5m | V-World | 지형 기복 (남산 등) | |
| 배경지도 / 좌표계 | V-World 2D API | 뷰어 베이스 레이어 | |

> Isopolis는 Google Photorealistic 3D Tiles를 썼고 "텍스처가 있어야 학습에 유리"하다고 했다.
> **V-World 주요 도심 LOD3~4 = 실사 텍스처 3D 건물**이므로 동등한 역할이 가능하다고 판단한다.
> 다만 **실제 화질·커버리지는 반드시 PoC로 검증해야 한다.** (→ 5단계 Phase 0)

### 4-B. 관광 레이어용 (차별화 축)

| 데이터 | 출처 | 용도 |
|---|---|---|
| 관광지·음식점·숙박 POI | **한국관광공사 TourAPI** | 지도 위 관광 스팟 마커 |
| 문화재 정보 | 국가유산청 API | 경복궁·궁궐·한옥 등 해설 |
| POI 검색 / 좌표 변환 | **카카오 로컬 API** | 장소 검색, 주소↔좌표 |
| **보행자 경로** | **Tmap API** | **관광 코스 추천 — 핵심 기능** |
| 관광객 통계·유동인구·상권 | 서울 열린데이터광장 | 혼잡도, 추천 시간대 |
| **지하철** | **서울교통공사 / 서울 열린데이터광장 (역 좌표·출입구·노선)** | **역 스프라이트 + 노선 라인. 범위 내 역만 선별** |
| 버스 | 서울 열린데이터광장 | 후순위 |

> **Tmap 보행자 경로 + TourAPI POI = "픽셀 지도 위를 걷는 관광 코스"**.
> Isopolis의 가이드 투어(4개)에 대응하되, **실제 보행 경로 데이터 기반**이라는 점이 다르다.

#### 지하철 — 범위 내 노선만 부분 구현

전 노선은 하지 않는다. **렌더 범위에 걸치는 역만** 다룬다.
도심 관광축(경복궁~남산) 기준 대략 다음 정도:

- 3호선: 경복궁 · 안국 · 종로3가
- 1호선: 종각 · 종로3가 · 시청 · 서울역
- 2호선: 시청 · 을지로입구
- 4호선: 명동 · 회현 · 서울역

구현 범위:
- **역 위치를 픽셀 스프라이트로 표시** (출입구 좌표까지 되면 더 좋음)
- **노선 색상 라인을 지도 위에 오버레이** — 실제 선형이 아니라 역 간 연결로 단순화해도 무방
- 관광 POI ↔ 최근접 역 연결 ("이 관광지는 안국역 도보 5분")

> 프로토타입이므로 **정확한 지하 선형·환승 구조는 재현하지 않는다.**
> 목적은 "픽셀 지도가 실제 교통망과 붙는다"를 보여주는 것.

### 4-C. 후순위 (여력 있을 때)

국토부 실거래가, 건축물대장 — 관광 컨셉과 결이 다르므로 이번엔 제외.

[Phase 0] 타당성 검증 ✔ 완료 (09-03)

[Phase 2] 스프라이트셋 제작  (구 '학습 데이터' 대체)
   용도x구조 조합별 픽셀 스프라이트 수십 종 -> AI 생성 + 사람 선별
[Phase 3] 스프라이트 적용

[Phase 4] 타일 피라미드
   타일 분할 -> 다단계 다운샘플 -> 정적 파일
[Phase 5] 뷰어 + 레이어
   커스텀 Canvas 뷰어 + TourAPI POI + 문화재 + 지하철 + Tmap 코스 + URL 해시

### A안의 데이터 → 표현 매핑

| 데이터 속성 | 출처 | 무엇을 결정하나 |
|---|---|---|
| `ag_geom` 폴리곤 | `dt_d198` | 건물 형상·위치 |
| `ground_floor_co` 지상층수 | `dt_d198` | 높이 (층고 상수 × 층수) |
| `buld_prpos_cl_code_nm` 용도 대분류 | `dt_d198` | 팔레트·스프라이트 선택 |
| `strct_code_nm` 구조 | `dt_d198` | **목구조 → 기와지붕/처마** |
| `buld_nm`+`buld_dong_nm` | `dt_d198` | 라벨 (예: 경복궁 경회루) |

| DEM 5m | V-World | 지형 기복 |

### 형태는 데이터, 외형은 AI — 역할 분담

데이터가 주는 것과 안 주는 것이 명확히 갈린다. **그 경계가 AI의 자리다.**

| 구성 | 무엇 | 어디서 | AI 개입 |
|---|---|---|---|
| **형태(mass)** | 바닥 폴리곤·높이·위치 | `dt_d198` | ❌ 없음. 좌표를 건드리지 않는다 |
| **지붕 기하** | 맞배·팔작·처마 | **절차적 생성** (footprint→능선) | ❌ AI보다 정확하고 싸다 |
| **표면 텍스처** | 창문·간판·기와 패턴 | **AI 생성 스프라이트** | ✅ 수십 종 |
| **랜드마크 외형** | 근정전·경회루·광화문 등 | **국가유산청 사진 → AI 변환** | ✅ 아래 참조 |

#### 궁궐 랜드마크 — 생성이 아니라 "변환"

일반 한옥 2,352동은 개별 정체성이 없으므로 AI 기와 스프라이트로 충분하다.
**궁궐 98동은 다르다.** 근정전은 중층 팔작지붕, 경회루는 벽 없는 누각, 광화문은 문루로
형태가 서로 다르고 실물이 널리 알려져 있다.

AI에게 **"한국 궁궐을 그려줘"라고 하면 그럴듯하지만 틀린 근정전**이 나온다.
국토교통부 주관 공간정보 공모전에서 **정확성 15점**이 걸린 문제이고,
1차 통과 시 **대국민 공개검증 10일**도 있다.
Isopolis가 금문교에서 겪은 것과 같은 유형이다 ([RESEARCH-isopolis.md](RESEARCH-isopolis.md) §3).

**해법: 상상하게 하지 말고 변환시킨다.**

국가유산청이 문화유산 사진을 **OpenAPI로 개방**하고 있고 **공공누리** 라이선스다.

```
국가유산청 개방 사진 (근정전 실물)
        ↓ Qwen-Image-Edit 로컬 실행 (image-to-image)
아이소메트릭 픽셀아트 스프라이트
        ↓ 사람이 10~15개 실물과 대조
지도 배치
```

실물 사진을 입력으로 주면 결과는 **근정전이다.** 출처도 국가유산청으로 댈 수 있다.
Qwen-Image-Edit는 원래 image-to-image 모델이라 정확히 이 용도다.

**부수 효과**: V-World(공간정보) + 국가유산청(문화유산) **두 국가 데이터를 AI로 결합**하는
구조가 되어 데이터 다양성·수급성 점수에도 기여한다.

**확인해야 할 것** — 사진은 정면·사각이고 우리 투영은 방위 22.5°/고도 30° 고정이다.
각도 변환 품질이 관건이라 **Phase 2 첫날 1개로 검증**한다.
실패하면 형식 파라미터 + 절차적 생성으로 후퇴한다.

### 서울 고유의 난점 — A안에서의 대응

| 난점 | B안이었다면 | **A안 대응** |
|---|---|---|
| **한옥·기와지붕·궁궐** | 학습 데이터에 넣고 기도 | ✔ **`strct_code_nm` 목구조로 자동 판별.** PoC에서 경복궁 전각 113동 확인 |
| 고층 아파트 밀집 | 모델이 뭉갤 위험 | 층수 그대로 압출. 문제 없음 |
| **간판 밀도** | 픽셀 해상도에서 뭉개짐 | 생성 대상 아님. **어노테이션 레이어**로 분리 |
| 남산 등 급경사 | 고도 표현 실패 (Isopolis가 비판받은 지점) | DEM 5m를 렌더에 반영 — **차별화 기회** |

| 좌표계 혼재 | — | 전역 ENU 접선평면으로 통일. PoC에서 검증됨 |

> A안으로 바꾸면서 **환각 계열 난점(물·궁궐·간판)이 구조적으로 사라졌다.**
> 남은 건 "밋밋함"이고, 그건 스프라이트로 푸는 문제다.

| 리스크 | 심각도 | 대응 |

## 7. 최소 성공 조건 / 욕심 목록

**반드시 되어야 하는 것 (MVP)**
- 도심 관광축 픽셀 지도가 끊기지 않고 팬·줌된다
- 관광 POI가 지도 위에 표시되고 클릭하면 정보가 나온다
- 공유 가능한 링크 (URL 해시 상태)
- 범위 내 지하철역 표시 + 노선 오버레이 (부분)

**되면 좋은 것**
- Tmap 보행 경로 기반 관광 코스 1~3개

## 8-B. 모델 선택과 라이선스 — **결론: 나노바나나 사용 안 함**

파이프라인에서 생성 모델은 **두 군데**에 쓰인다. 역할이 다르므로 따로 판단해야 한다.

| 역할 | 무엇 | Isopolis의 선택 | **본 프로젝트** |
|---|---|---|---|
| ① 정답 픽셀아트 100쌍 생성 | 학습 데이터 만들기 | **Nano Banana** | **Qwen-Image / Qwen-Image-Edit (로컬)** |
| ② 파인튜닝 + 대량 타일 생성 | 실제 지도 생성 | Qwen-Image-Edit-2511 + LoRA | 동일 |

② 는 애초에 나노바나나로 불가능하다. **파인튜닝을 지원하지 않는 폐쇄형 API 모델**이다.
쟁점은 ① 뿐이다.

### 왜 ①에서도 나노바나나를 배제하는가

Gemini API 추가 약관(https://ai.google.dev/gemini-api/terms)에 다음 조항이 있다.

> "You may not use the Services to develop models that compete with the Services...
> You also may not attempt to reverse engineer, extract or replicate any component."

> "You will not, and will not allow your end user... to ... **train on**" (출력물에 대해)

**출력물을 다른 모델 학습에 쓰는 것이 명시적 금지 대상이다.**
①의 용도가 정확히 "출력물로 LoRA를 학습시키는 것"이므로 정면으로 걸린다.

- 픽셀아트 스타일 LoRA가 Gemini와 "경쟁"하느냐는 해석의 여지가 있지만,
  **`train on` 조항은 해석의 여지가 좁다.**
- 이 공모전은 1차 통과 시 **대국민 온라인 공개검증 10일 이상**을 거치고,
  저작권 위반 확인 시 **입상 취소·환수**다. 해석 다툼을 안고 갈 자리가 아니다.
- 참고: **Isopolis도 이 경로를 썼고**, HN에서 공정이용 문제를 지적받았다.
  **레퍼런스를 그대로 따라하면 안 되는 지점이다.**

### 채택: Qwen 계열로 전 과정 통일 (Apache 2.0)

- Qwen-Image (20B, T2I) · Qwen-Image-Edit-2511 (20B, I2I) 모두 **Apache 2.0**
- **로컬(자체 호스팅) 실행 시 출력물 사용에 제한 없음**
- ⚠️ **단, Qwen Chat 호스팅 서비스는 비상업 이용 제한 조항이 있다. 반드시 직접 돌린다.**

#### "직접 돌린다"의 정확한 의미

내 PC라는 뜻이 아니라 **가중치를 내가 통제하는 환경에서 실행한다**는 뜻이다.
빌린 클라우드 GPU도 여기 포함된다.

| 방식 | 적용 규칙 | 가능 |
|---|---|---|
| Gemini API (나노바나나) | Google 약관 — `train on` 금지 | ❌ |
| Qwen **Chat** (호스팅 서비스) | Alibaba 약관 — 비상업 제한 | ❌ |
| Qwen 가중치를 내 PC에서 실행 | Apache 2.0만 | ✅ |
| Qwen 가중치를 **빌린 GPU**에서 실행 | Apache 2.0만 | ✅ |
| 서드파티 서빙 API (Replicate·fal 등) | **각 서비스 약관 별도 확인 필요** | ⚠️ 회색지대 |

**현실적으로는 GPU 대여가 답이다.** 20B bf16 = 가중치만 약 40GB라
RTX 4090(24GB)급으로는 양자화·오프로딩 없이 불가능하고, 학습은 더 어렵다.

- Isopolis 실적: Modal H100, 학습 2~3시간 × 2회 = **$20~30**
- 본 프로젝트 추정: 학습 + 생성(~150회) + 시행착오 → H100 15~20시간 → **$40~80**
- 대여처(Modal / RunPod / Vast.ai 등)는 **Phase 3에서 결정**. 지금 정하면 PoC 결과에 뒤집힌다.

> 나노바나나 대비 추가 비용은 수만 원 수준. **파이프라인 구조는 바뀌지 않는다.**
> 공개검증을 감안하면 서드파티 서빙보다 **직접 대여가 설명하기 깔끔하다.**

**결과적으로 학습 입력 → 베이스 모델 → 산출물까지 전 과정이 Apache 2.0 + 공공데이터로 정리된다.**

### 이게 오히려 점수가 된다

"전 과정 오픈 라이선스"는 방어 논리가 아니라 **가산점 요소**다.

- **데이터 수급성(20점)**: 누구나 같은 경로로 재현 가능
- **지속성·활용성·파급성(2차)**: 폐쇄 API 의존이 없어 타 도시·타 기관이 그대로 이어받을 수 있음
- 국토부·공간정보산업진흥원 주관 공모전의 성격(공공 활용·공유)과도 정합

### 감수하는 것

정답 픽셀아트 품질이 나노바나나보다 떨어질 가능성이 있다.
→ **Phase 2에서 사람이 직접 선별(curation)해 보완한다.** 100쌍은 눈으로 고를 수 있는 양이다.
→ 그래도 부족하면 **직접 픽셀아트 제작 또는 오픈 라이선스 에셋**으로 일부 대체.
