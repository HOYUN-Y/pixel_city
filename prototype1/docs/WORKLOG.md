## 2026-09-13 — 정사영상에서 건물별 지붕색 (비목조 이웃 동일색 32.0% -> 10.3%)

지붕색이 주용도로만 갈리는데 **주용도는 공간적으로 군집한다** — 근생은 근생끼리 붙어
있다. 그래서 조합이 102종이어도 화면에서는 덩어리로 보였다. V-World 정사영상에서
실제 색을 가져와 깼다. **AI는 안 썼다** — 외곽선 안의 화소 중앙값이면 된다.

### 데이터 경로 — 3D가 아니라 2차원 항공영상이다

V-World 3D DATA API는 중단됐고 3차원 데이터는 '공개제한'이라 뷰어 화면 캡처도 같은
제한을 받는다. **정사영상은 별개 데이터셋**이고 WMTS로 공개돼 있다. 기존 키로 확인했다.

```
https://api.vworld.kr/req/wmts/1.0.0/{KEY}/Satellite/{z}/{y}/{x}.jpeg
⚠️ 경로 순서가 {z}/{y}/{x}다. x/y를 바꾸면 "서비스 제공영역이 아닙니다"가 온다
⚠️ 영상 레이어는 Satellite뿐. Base는 같은 좌표에서 404
z18 = 0.473 m/px · bbox 600타일 · 8.2MB · 수집 실패 0건
```

### 표본 — 성공률 97.2%, 계획의 예상이 틀렸다

계획에는 "고층은 침식하면 남는 게 없어 실패하는 게 정상"이라고 썼다. **틀렸다.**

```
0~10m  3907/4025 (97%)    20~50m  442/461 (96%)
10~20m 2271/2310 (98%)    50m+    183/195 (94%)
```

고층도 94%가 성공한다. 바닥면적이 크기 때문이다(p95 687m²). 성공률이 높다고 정확한
건 아니지만, **외곽선을 영상에 겹쳐 눈으로 확인**했다 — 정합이 정확하다.

침식 반경 = `0.078 × 높이 / (m/px)`, 최소 1화소. 서울 도심 건물의 90%가 20m 이하라
수평 변위가 1.5m 이하 = z18에서 3.2화소다. 전체 6,991동 표본 추출 **49초**.

### ⚠️ 서울 옥상은 녹색이다 — 기대한 다채로움이 안 나온다

```
색상환 120~150° 31.5%  +  150~180° 35.8%  =  67.3%
명도 p10/p50/p90 = 56 / 94 / 154   (기존 규칙색 지붕은 명도 171)
```

**녹색 방수 도료**다. k=12 군집의 중심 12개 중 9개가 같은 녹색조의 명도 램프가 된다.
타일에서 파란 지붕이 눈에 띄었지만 면적 비중으로는 소수였다. z18과 z19가 통계적으로
동일해(같은 촬영본) 줌을 올려도 달라지지 않는다.

### ⚠️ 채도를 올리면 **나빠진다** — 실측으로 반증됐다

`iso2.py`로 전체 렌더를 세 번 돌려 비교했다(파일은 안 고치고 `bld_colors`만 임시로 덮음).

| 안 | 이웃 동일색 | 평균거리 | 명도중앙 |
|---|---|---|---|
| 현재(규칙색) | 45.3% | 34.3 | 171 |
| 실측 그대로 | 18.3% | 60.4 | 98 |
| **명도만 +25%** ← 채택 | **15.9%** | 72.9 | 121 |
| 명도+채도 ×1.45 | 17.7% | 80.0 | 135 |

**채도를 올리면 15.9% -> 17.7%로 나빠진다.** 색상이 비슷한 것끼리 채도를 올리면 서로
더 가까워지기 때문이다. 화면으로도 형광 연두가 튄다. 그래서 `ortho_lift`의 채도배율이 1.00이다.
명도를 올리는 건 미화가 아니라 **그림자 보정**이기도 하다 — 좁은 골목 건물은 지붕 상당
부분이 그늘에 들어가 표본이 실제보다 어둡다.

### ⚠️ 팔레트 회피 재배치를 넣었다가 뺐다

중심이 기존 팔레트 색과 가까우면 "표본에서 가장 먼 색으로 다시 심는" 로직을 넣었다.
**극단값에 중심을 박아버렸다** — 7~14동짜리 형광 주황(255,155,95)·하늘(141,222,249)
중심이 3개 생기고 최대 셀이 14.8% -> **23.6%로 나빠졌다.**

애초에 불필요했다. 재배치 없이 군집한 12색과 기존 137색의 **최소거리가 12.2**라
selfcheck 기준(14)을 이미 만족한다. 빈 버킷도 32,640개다. 걷어내고 진단(`nearest_gap`)만 남겼다.

> ⚠️ **1차 구현에서 목조를 통째로 빠뜨렸고, 내 미리보기가 그걸 놓쳤다.**
> 파이썬 미리보기는 목조에도 실측을 적용해 15.9%를 예측했는데 실제 `palette()`는

> 미리보기와 구현이 다르면 지표가 거짓말을 한다.

### 한옥은 태우고 궁궐은 뺀다

`ortho_hanok` 스위치. 한옥 2,352동은 실측을 타고 **궁궐 전각 98동은 스위치와 무관하게
언제나 제외**한다 — 랜드마크라 기와색이 정체성이고, 표본이 나무 그늘에 오염되면
근정전이 녹회색이 된다. 궁궐이 남긴 88.8%가 전체의 1.4%를 차지해 **15% 아래로는
안 내려간다. 그건 의도한 바닥이다.**

**처마 파생색(x0.72 / x0.62)은 기존 기와에서 나온 것을 그대로 쓴다.** 실측 12색마다
파생 2개를 구우면 +24색이라 예산 160을 넘는다(149 + 24 = 173). 처마는 그늘진 면이라
지붕과 색이 조금 어긋나도 읽히지 않는다. **팔레트 추가 0색.**

> ⚠️ **화면 평균 채도는 목표 미달이다.** 0.129 -> **0.124**로 오히려 미세하게 내려갔다

## 2026-09-13 — 팔레트 충돌 assert가 틀려 있었다 (재현성 없음)

정사영상 지붕색 작업을 시작하면서 팔레트에 12색을 더해야 하는데, **충돌을 알려줄 지표가
거짓 신호를 내고 있었다.** 색을 넣기 전에 먼저 고쳤다.

### 증상 — 커밋본에서 이미 실패 중이던 항목

```
팔레트 색이 엉뚱한 색으로 스냅된다 37  (64,78,94) -> (77,80,82)   거리 17.8 > 14
```

### 원인 — `PAL_LUT`는 미리 계산한 표가 아니라 **메모 캐시**다

`nearest()`의 마지막 줄이 `PAL_LUT[key] = best`다. 버킷(채널당 5비트) 하나에 답을
**하나만** 저장하므로, **그 버킷을 먼저 질의한 픽셀이 답을 정해버린다.**

버킷 (8,9,11)을 전수 조사했다:

```
512색 중  508색 -> (64,78,94)      <- 올바른 답
            4색 -> (77,80,82)      <- 모서리. 예: (71,79,88)은 9.27 vs 8.54로 후자가 더 가깝다
```

**그 모서리 4색이 먼저 렌더되면 버킷 전체가 뒤집힌다.** 그 뒤 팔레트 색 37이 자기
버킷을 질의하면 캐시된 (77,80,82)를 돌려받는다. 거리 17.8.

즉 **같은 코드가 렌더 이력에 따라 통과하기도 실패하기도 했다.** 재현성이 없는 assert였다.

**팔레트 구성 자체는 멀쩡하다.** LUT를 타지 않고 참 최근접을 직접 계산하니
**기하학적 실패 0건**이다. 버킷을 공유하는 색 쌍이 9곳 있지만 같은 버킷 안이라
최대 오차가 12.1(= √(3×7²))이고 육안으로 같은 색이다.

### 고친 것 — 기하는 assert, LUT 손실은 로그

assert가 잡아야 하는 건 "새 색을 넣었더니 멀리 있는 색과 뭉쳤다"이고 그건 **캐시와
무관한 순수 기하**다. `nearest()` 대신 LUT를 안 타는 `trueNearest()`로 검사한다.

버킷 공유로 인한 손실은 **5비트 LUT의 원리적 한계**지 팔레트의 결함이 아니다.
assert에서 내리고 로그로 바꿨다:

```
[pixel_city] 팔레트 137색 · 근사 중복 9건 · 버킷 공유 9곳(최대 오차 …) · 빈 버킷 32640
```

### 검증

**콜드 LUT와 웜 LUT(줌 0·2·4를 렌더한 뒤)의 결과가 완전히 같다.** 이게 핵심이다 —
전에는 이 둘이 달랐다. 팔레트 실패 **1건 → 0건**. 남은 selfcheck 실패는
"남산이 화면에서 솟는다" 하나이고 이건 별개 선재 결함이다.

> 빈 버킷이 32,640개다. 지붕색 12개를 더해도 버킷 여유는 문제가 아니다.
> 제약은 예산(`<= 160`)과 **기존 색과의 거리**뿐이다.

## 2026-09-13 — Isopolis 대조 측정: 차이는 파사드가 아니었다

사용자가 [sf.isopolis.city](https://sf.isopolis.city)와 나란히 놓고 *"결과물이 아쉽다,
특히 건물 디테일"*이라고 했다. 감으로 답하지 않으려고 양쪽 화면의 색 분포를 실측했다.

### 먼저 — **창문 격자는 이미 Isopolis와 동등하다**

Isopolis를 LVL 7/8까지 확대해 보니 파사드 처리가 오늘 넣은 것과 거의 같은 방식이다.
**파사드는 문제가 아니었다.** 차이는 전부 그 바깥에 있었다.

| 지표 | pixel_city | Isopolis |
|---|---|---|
| **팔레트** 평균 채도 | **0.232** | 0.227 — **동등** |
| **화면** 평균 채도 | **0.129** | **0.227** |
| 단일 색 최대 점유 | **16.5%** (도로) | 5.5% (하늘·바다) |
| 유채색의 단일 색상 구간 | **65.6%** (210~240° 청색) | 34.9% (30~60° 황토) |

**팔레트에는 따뜻한 색이 충분한데 화면에 안 나온다.** 면적이 어디로 가는지 뜯어보니:

```
road            16.5%   ┐
ground           6.9%   ├ 청회색 계열 합 약 56%
wall_m.콘크리트 32.5%   ┘   (110,118,132 / 123,132,148 / 152,160,172 / 170,179,193)
park             3.9%
heri             3.7%
roof_g.업무시설  3.0%
```

### ⚠️ 내 측정 지표가 틀린 그림을 주고 있었다

`paletteSpread`는 **동수**를 센다. "최대 셀 13.4% / 조합 102종"은 그래서 나온 숫자다.
작은 단독주택 한 채와 32층 오피스를 같은 한 표로 셌다. **화면을 채우는 건 큰 건물이다.**

같은 걸 **면적×높이**로 다시 쟀다:

| | 동수 | 면적×높이 |
|---|---|---|
| 조합(지붕×벽×벽) 최대 셀 | 13.4% | **20.3%** |
| **벽 재질 최대(콘크리트)** | 42.2% | **82.7%** |

조합 지표는 1.5배 나빠질 뿐이라 파국이 아니다. **진짜 쏠림은 축을 하나 떼어야 보인다** —
벽 재질축이 면적으로 콘크리트 82.7%다. 색 변주의 두 축 중 하나가 사실상 상수다.

> 처음 이 숫자를 80.1%로 적었는데, 즉석 측정의 높이 가중이 `max(1, h/10)`이라
> 코드(`max(1, h)`)와 달랐다. **82.7%가 맞다.**

### 그리고 조합 수로는 안 잡히는 것 — 이웃과 같은 색

```
최근접 이웃과 지붕색 평균거리   36.2
거의 같은 색(거리<10) 비율     43.5%
```

**인접 건물의 43.5%가 사실상 같은 지붕색이다.** 지붕색이 주용도로만 갈리는데
**용도는 공간적으로 군집한다** — 근생은 근생끼리, 주택은 주택끼리 붙어 있다.
그래서 "조합 102종"이 화면에서는 덩어리로 보인다. 축을 데이터에서만 뽑은 대가다.

### 넣은 것 — 지표 두 개

| 함수 | 내는 값 | 2026-09-13 기준선 |
|---|---|---|
| `paletteSpread()` | `wTopShare` 면적 기준 조합 쏠림 | **0.203** |
| | `matShare` 면적 기준 **단일 축** 쏠림 | **0.827** |
| `neighborContrast()` | `sameShare` 이웃과 동일색 비율 | **0.435** |

아니라 "더 나빠지지 않았다"는 뜻이다. 목표는 `matShare <= 0.50`, `sameShare <= 0.10`.

`neighborContrast`는 이웃 탐색이 O(n²)라 전수면 **580ms**다. 매 로드에 너무 비싸서

### 설계 — 좌표계는 파이썬에, JS는 직사각 배열만

`terrain.py`가 DEM을 **우리 ENU 프레임 위 정규격자로 리샘플**한다. ENU는 lon/lat의
선형 사상이라(`e=(lon-lon0)*mlon`) ENU 정규격자 = EPSG:4326 축정렬 격자이고,
`rasterio.warp.reproject` + `Resampling.bilinear` **한 호출**로 CRS 변환·보간·nodata가
끝난다. 점별 변환 루프가 필요 없다.

- **프레임은 `web/data/meta.json`에서 읽는다.** `import export`는 `export → iso2 → PIL`
  연쇄로 죽고(Pillow 없음), `origin()` 복붙은 프레임이 분기한다. `meta.json`은 커밋된
  `city.json`과 같은 프레임을 이미 데이터로 갖고 있어 불일치가 구조적으로 불가능하다.
- **격자 47×60 = 2,820점, 패드 900m(10셀).** 패드가 없으면 위 발견 때문에 남산 정상이
  격자 끝 절벽에 걸린다. 패드 동쪽 106칸이 도엽 밖이라 최근접 유효값으로 메웠다
  (패드의 목적이 "프레임 끝에서 지형이 끊기지 않게"이므로 바깥으로 평평히 잇는 게 맞다).
- **datum `z0` = ENU 원점(bbox 중심, 평지 도심)의 표고 26.8m.** 상대고도 -10.1~259.7m.
  평지 도심이 화면 중앙에 남아 기존 프레이밍·URL 해시가 유지된다.
- **과장은 값에 굽지 않고 `exag` 필드로 살려 뒀다.** 교정할 때 `terrain.json`의 숫자
  하나만 고치고 새로고침하면 되고 **원본 `.img`가 다시 필요하지 않다.**

### `sy`에 지형을 무조건 접으면 안 된다 — 건물 지붕이 기운다

처음 계획은 "`sy`에 `zAt`를 접으면 기존 호출부 14곳이 공짜로 따라온다"였다.
**평면 레이어는 맞지만 건물은 깨진다.** 정점별 표고는 건물 바닥을 비평면으로 만들고,
90m DEM 최대 셀 경사 0.39에서 20~40m 풋프린트면 Δz 8~15m → 확대 단계에서 지붕이
7~13 아트픽셀 기울어진다. 2~5층 높이만큼 기운 상자는 스크린샷에서 버그로 읽힌다.

해법: `sy(e, n, h, z)`의 **4번째 인자를 옵션으로** 뒀다. 주면 그 값이 기준면(건물 =
평면 기초), 안 주면 지형을 샘플(지면 밀착). 기존 `sy(...,0)` 14곳은 **편집 없이** 지형을 탄다.

- 건물은 로드 시 `b.z = zAt(링 중심)` 한 번. 프레임당 `zAt` 호출이 정점당 → 0회로 줄었다
- `pick()`의 `drop`은 `z`가 양쪽에 같이 들어가 **소거**되어 지형 도입 전과 동일하다.
  `b.z` 전달만 하면 끝 (실측 확인: 남산 11px vs 평지 10px, 반올림 ±1)
- **카메라 앵커는 z=0 평면 고정.** 앵커에 `zAt`를 넣으면 팬할 때 세계가 상하로 펌핑하고
  `visible()`의 `oy`·`screenToWorld`까지 따라가야 해서 diff가 3배가 된다

**3차 실패 — 사용자 지적 "산이 잘 안 보여". 근본 원인이었다.**

경사 음영만으로는 산이 보이지 않는다. **경사는 기울기의 *변화*만 보여주고 높이 자체를
보여주지 않는다 — 균일한 사면은 균일한 톤이 된다.** 실측으로 확인했다:

```
남산 종단면 (E=459)   표고 232→31m (200m 하강)
  쓰인 음영 단계: 2, 3   ← 두 개뿐
  단계 2 휘도 72.6 = 평지 공원 휘도 72.6   ← 산이 평지와 완전히 같은 색
```

**지도가 산을 보여주는 방식은 표고별 색조(hypsometric tint)다.** 단계 공식을 바꿨다:

```
단계 = neutral + round(표고/zband) - round(경사*gain)     # 표고가 주, 경사가 보조
```

램프를 5단 → **8단**으로 늘리고 `zband=50m`, `gain 4→3`으로 맞췄다.

**램프는 채널별 배율이다** — 위로 갈수록 R>G>B가 되어 **밝아지면서 난색으로 이동**한다
(공원: `[58,78,62]` 초록 → `[190,212,119]` 황록). 휘도만 올리는 것보다 눈에 잘 띄고,
`heri`의 녹색 채널(92)이 255를 넘는 클리핑도 피한다 — 밝기만으로 9단을 시도했을 때

`zband=50m`은 도심 대역폭(41.5m)보다 크고, **남산 259m가 정확히 +5밴드로 램프 상단에 닿는다.**

### 팔레트 — 5비트 LUT 충돌과 assert 정정

`nearest()`는 채널당 `>>3`으로 버킷팅하므로 **모든 채널에서 8 미만 차이인 색 둘은
구분되지 않는다.** `C.ground=[54,60,68]`에 `×0.72…×1.28`을 쓰면 단계 간 차가 7로
충돌 직전이다. 램프 계수를 `[0.50, 0.74, 1.00, 1.28, 1.58, 1.90, 2.24]`로 벌려 버킷을
전부 분리했다 (최대 채널값 206으로 255 클립도 없다). 팔레트 57 → **75색**.

selfcheck의 "팔레트 색은 자기 자신으로 스냅"을 인덱스 0 하나에서 전수로 바꾸려다
**요구를 잘못 잡았다는 걸 알았다.** 충돌하는 색은 정의상 채널당 8 미만 차이 =
육안으로 같은 색이므로, 자기 자신을 요구하면 무해한 경우까지 계속 걸린다.
잡아야 하는 것은 **"멀리 있는 색으로 스냅되는 것"**이다 → 스냅 거리 < 14로 바꿨다.

부수 확인: **근사 중복 2건은 지형 도입 전부터 있었다** (문교사회용 처마 파생 ~ 한옥 벽,
주거용 파생 ~ 공업용 파생). 채널당 4 이하 차이라 화면에서 구분되지 않아 그대로 둔다.

### 두 렌더러 일치 — 상수를 데이터로 내려보냈다

음영 상수를 JS에 하드코딩하지 않고 **`terrain.json`에 실어 양쪽이 같은 숫자를 읽게** 했다.
정본은 `style.json`이지만 그 경로는 `export.py` 재실행(= V-World 재수집)을 요구해 지금
못 돌린다. `terrain.py`가 `style.json` → `terrain.json`으로 전달한다.

`terrain.py`에 `zq()`(= JS `zAt`)와 `cells()`(= JS `buildTerrainCells`)를 두고
`iso2.py`가 그것을 **import해 재사용**한다. 파이썬 쪽 구현은 하나다.

**이식 검증 (골든값보다 강하다)**

| 항목 | 결과 |
|---|---|
| `zAt` vs `zq` 184점 (격자점·셀중앙·마지막노드·격자밖) | 최대 오차 **2.8e-14** (배정도 한계) |
| `buildTerrainCells` vs `cells` 셀 목록 | **1,045개 전부 동일** (단계분포·직렬 길이까지) |
| `terrain.json` 골든 3건 | JS·파이썬 일치 |
| 기존 투영 골든 5건 | **영향 없음** — `checkGolden`은 `projU/projV`를 직접 부르고 `sy`를 안 거친다 |

### 부수 발견 — `round()` 반올림 규칙이 파이썬/JS가 다르다

파이썬 `round()`는 0.5에서 **짝수로** 가고 JS `Math.round`는 **위로** 간다
(`round(2.5)`: 파이썬 2, JS 3). 음영 단계 계산에 `round`가 두 번 들어가므로
정확히 .5가 나오는 셀에서 두 렌더러가 갈린다. `terrain.py`에 `_rnd(x) =
floor(x + 0.5)`를 두어 JS와 맞췄다. 909셀 일치는 이걸 맞춘 뒤의 결과다.

### ⚠️ `iso2.py`의 ENU 원점을 정정했다 (조용한 분기였다)

`iso2.py` `__main__`은 ENU 원점을 **건물 정점 평균**으로 잡고 있었는데
`export.py origin()`·`terrain.py frame()`은 **bbox 중심**이다. 그대로 두면
`terrain.json`의 표고가 엉뚱한 위치에 얹힌다. bbox 중심으로 통일했다.

`fit()`이 프레임 기준으로 중심을 잡으므로 **기존 출력 구도는 변하지 않는다**
(건물과 프레임이 같이 이동해 상쇄된다). `export.py`의 주석이 이미
"점 평균이 아니라 bbox라서 재현 가능하다"고 적어둔 지점이었다.

### 남은 것 / 주의

- **`iso2.py`의 실데이터 전체 렌더는 아직 못 돌렸다.** `cache_*`가 `.gitignore` 대상이라

  검증했지만 6,985동 실렌더는 **키를 받은 뒤 `collect.py` 재수집 → 재확인**해야 한다.
- **`iso2.py`는 하천을 `heris`에 합쳐 넘겨 국가유산 색으로 그린다** (`RIVER` 상수가
  정의만 되고 안 쓰인다). 뷰어는 `C.river`로 그린다 — **기존 렌더러 분기**다.
  이번 작업 범위가 아니라 손대지 않았다. 발견 사실로 남긴다.
- **서울타워는 V-World 원본에서 0.4m × 0.4m (면적 0.1m²)** 점에 가까운 폴리곤이다.
  화면에서 0×1 픽셀이라 어떤 줌에서도 클릭이 안 된다. DEM과 무관한 기존 데이터 특성.
- 알려진 한계는 코드에 `ponytail:` 주석으로 표시했다 — 지형을 건물보다 먼저 전부 그려
  능선 뒤 ~400m(`z·cotΦ`) 띠가 겹치는 것, 도로 정점만 표고를 받는 것, 카메라 앵커 고정.
  건물 간 페인터 정렬은 **재수출 불필요**: 순서 뒤집힘 조건이 경사 60° 초과인데
  90m DEM 최대 셀 경사는 21°다.

큰 산괴(북한산·한라산)는 잘 잡지만 도심 소규모 급경사에 약하다.
단순 격자 평활만으로 설명하기 어려운 수준이며, 원본 소스나 리샘플링 문제로 보인다.

**2. 대상 구역이 26 × 38 픽셀뿐이다.**
7.86km²를 90m 격자로 나누면 그게 전부다. 화면 축척 1~3.5m/px에서
한 셀이 26~90픽셀 블록이라 보간해도 지형이 뭉툭한 덩어리로 나온다.
구역 내 고도 범위는 21~246m, 평균 49m.

## 2026-09-04 — Phase 2 재구성: "픽셀아트답게" + 랜드마크 방식 확정

### 계기: 지금 결과물이 픽셀아트가 아니다

사용자 지적. 확인해보니 **계획이 원인의 절반만 덮고 있었다.**
원래 Phase 2는 "AI 스프라이트"만 다뤘는데, 진짜 원인은 텍스처가 아니었다.

| 원인 | 기존 계획에 있었나 |
|---|---|
| **① 픽셀 격자 부재** | ❌ **없음. 근본 원인** |
| ② 팔레트 제한 없음 | ❌ 없음 |
| ③ 표면 텍스처 없음 | ✅ 있음 |

**①이 핵심이다.** `poc/iso2.py`는 작게 그린 뒤 `Image.NEAREST`로 정수배 확대해
픽셀 경계가 살아 있다(`ZOOM=3`). 그런데 **브라우저 뷰어는 화면 해상도에 바로 그려서 이걸 잃었다.**
`imageSmoothingEnabled=false`는 이미지 확대에만 걸리고 Canvas 도형의 안티앨리어싱은 못 막는다.
→ **뷰어가 파이썬 렌더러보다 덜 픽셀아트다.** ②로 옮기며 잃은 것을 내가 짚지 못했다.

**해법**: 오프스크린 캔버스(1/N)에 그린 뒤 정수배 NEAREST 확대.
부수 효과로 렌더 면적이 1/N²이라 112ms가 20ms 아래로 떨어진다.

### Phase 2를 6단계로 재구성

- **2-A 픽셀 격자 복원** ← 최우선. 반나절. 효과 최대
- 2-B 팔레트 32~48색 제한 + 디더링
- 2-C 지붕 기하 절차적 생성 (맞배/팔작) — **AI 아님**
- 2-D 표면 텍스처 — **여기가 AI 담당**
- 2-E 랜드마크 형식 지정
- 2-F JS 렌더러 반영

**순서를 바꾼 이유**: 2-A/2-B를 먼저 하면 텍스처 없이도 즉시 픽셀아트처럼 보인다.
기존 계획은 2-D(AI 텍스처)부터 하게 돼 있었다.

| 구성 | 어디서 | AI |
|---|---|---|
| 형태(바닥·높이·위치) | `dt_d198` | ❌ 좌표를 건드리지 않는다 |

| 표면 텍스처 | AI 스프라이트 | ✅ |
| 랜드마크 외형 | 형식 지정 + 절차적 생성 | ❌ |

### 랜드마크: 방식이 두 번 바뀌었다 (최종: AI 변환)

**1차** — "수제 스프라이트"라고 적었으나 표현이 모호했다.

세 가지로 갈린다.
1. 사람이 픽셀 에디터로 그림 — 전각 1개당 1~3시간, 15개면 20~40시간
2. 형식을 파라미터로 지정하고 렌더러가 그림
3. AI

**사용자가 "직접 그리는 건 현재 시점에서 불가능"하다고 확인 → ① 탈락, ②로 잡았다.**

**2차 (최종)** — 사용자가 "AI를 쓰는 게 나을 것 같다"고 제안. **재검토 결과 맞는 지적이었다.**

내가 ②를 과대평가했다:
- **임의 footprint에서 팔작지붕을 정확히 만들려면 straight skeleton이 필요하다.**
  이걸 "쉽다"고 잡은 것이 오판이다. D-14에 감당할 기하 문제가 아니다
- 분야가 **GeoAI**인데 AI 비중이 텍스처뿐이면 정합성이 약하다
- ②로 나오는 근정전도 결국 "중층 팔작 상자"라 정확성 우위가 생각만큼 크지 않다

**내가 걱정한 "틀린 근정전"은 참조 이미지로 해결된다.**

**국가유산청이 문화유산 사진을 OpenAPI로 개방하고 공공누리 라이선스다** (48만 건 무료 개방).

```
국가유산청 개방 사진 (근정전 실물)
   -> Qwen-Image-Edit 로컬 실행 (image-to-image)
   -> 아이소메트릭 픽셀아트 스프라이트
   -> 사람이 10~15개 실물과 대조
   -> buld_nm 매칭 배치
```

**핵심은 "생성"이 아니라 "변환"이라는 점이다.**
"한국 궁궐을 그려줘"는 상상한 궁궐을 낳지만, **실물 사진을 입력으로 주면 그건 근정전이다.**
Qwen-Image-Edit가 원래 image-to-image 모델이라 정확히 이 용도다. 출처도 국가유산청으로 댈 수 있다.

**부수 효과**: V-World(공간정보) + 국가유산청(문화유산) 두 국가 데이터를 AI로 결합하는
구조가 되어 데이터 다양성·수급성에도 기여한다.
그리고 **팔작지붕 절차적 생성 문제가 통째로 사라진다** — 2-C는 일반 한옥 맞배지붕만 맡는다.

**확인해야 할 것 (Phase 2 첫날)**
1. **사진→아이소메트릭 각도 불일치.** 사진은 정면·사각, 우리 투영은 방위 22.5°/고도 30° 고정.
   변환 품질이 관건이라 **1개로 먼저 검증**한다
2. 국가유산청 API에 근정전·경회루·광화문 사진이 실제로 있는지, 해상도가 쓸 만한지 미확인

**실패 시 후퇴**: ②(형식 파라미터 + 절차적 생성)로 되돌린다. 지붕은 팔작 대신 단순화.
이 경로는 문서에 남겨둔다.

## 2026-09-04 — Phase 2-A 완료: 픽셀 격자 복원

### 무엇을 바꿨나

**아트 픽셀 좌표계를 도입했다.** 1/PIX 크기 오프스크린 캔버스에 그린 뒤
정수배 NEAREST로 확대해 화면에 붙인다. `poc/iso2.py`가 `Image.NEAREST`로 하는 것과 같다.

```
이전: 화면 해상도에 직접 그림     -> Canvas 안티앨리어싱, 가장자리가 뭉개짐
이후: 오프스크린(1/3)에 그림 -> 3배 NEAREST 확대 -> 픽셀 경계가 살아남
```

좌표계가 둘이 됐다.
- **아트 픽셀** — 오프스크린. `sx`/`sy`가 돌려주는 값. `s()`는 "미터/아트픽셀"
- **화면 픽셀** — 아트 픽셀 × PIX. 입력 이벤트와 라벨이 쓴다

`PIX`는 `poc/style.json`의 `pixel_size`(기본 3)에서 읽는다.
`SCALES`도 "미터/화면px"에서 **"미터/아트픽셀"**로 의미가 바뀌어 `[8, 4, 2, 1, 0.5]`로 재조정했다.

### 결과

| | 이전 | 이후 |
|---|---|---|
| 전체 6,991동 | 112ms | **81ms** |
| 확대 시 | 46ms | **24~48ms** |
| 가장자리 | 안티앨리어싱 | **계단식 픽셀** |

**렌더 면적이 1/9이라 더 빨라졌다.** 라벨은 화면 해상도 별도 레이어로 그려 선명함을 유지했다.

### 함께 고친 것

1. **기호 크기 고정** — 지하철 선·역·POI 마커가 월드 크기라 확대할수록 굵어졌다.
   기호는 물리적 대상이 아니므로 아트픽셀 기준 고정값(`SYM`)으로 바꿨다.
   지하철역은 원 대신 **픽셀 사각형**, POI는 한 줄씩 쌓은 **픽셀 삼각형**으로 그린다.
2. **건물 클릭이 지붕에서만 되던 문제** — 벽면을 클릭하면 안 잡혔다.
   압출은 화면상 수직 이동이므로 실루엣은 지붕 폴리곤을 아래로 쓸어내린 영역이다.
   높이 구간을 최대 6단계 샘플링해 벽면도 잡도록 고쳤다.
3. **선택 처리를 `pointerup`에서 `click`으로 이동** — 포인터 캡처 상황에 따라
   `pointerup`이 누락될 수 있다. `setPointerCapture`도 try/catch로 감쌌고
   `pointercancel`도 처리한다. 포인터 이벤트는 팬만 맡는다.
4. **자체 검증 추가** — `window.pixelCitySelfCheck()`로 점-내부 판정, 처마 확대,
   오프스크린 크기, 화면중심 역투영을 확인한다. 디버그 훅 `window.pixelCity`도 노출했다.

### 검증

- 투영 골든 값 5건 일치 (변경 후에도 유지)
- `pixelCitySelfCheck()` 통과
- 합성 이벤트로 **건물(국립고궁박물관) / 지하철역(경복궁역) / POI(국토발전전시관)** 세 종류 클릭 확인
- 콘솔 오류 0건

⚠️ **브라우저 자동화 도구의 마우스 클릭이 캔버스에 닿지 않아 실제 마우스 검증은 못 했다.**
`pick()`이 정확한 값을 돌려주고 합성 이벤트로는 세 종류 다 동작하므로 앱 문제는 아니라고
판단하지만, **실제 마우스로 한 번 확인이 필요하다.**

## 2026-09-04 — Phase 2-B 완료: 팔레트 양자화

### 문제 확인

픽셀 격자를 넣었는데도 경계가 완전히 딱 떨어지지 않았다.
**오프스크린 캔버스도 도형을 안티앨리어싱**하기 때문이다.
실측으로 확인했다 — 지도 영역만 색 수를 세니 **693색**이 나왔다
(팔레트로 정의한 색은 57개뿐인데).

`imageSmoothingEnabled = false`는 **이미지 확대**에만 걸린다.
Canvas의 `fill()`/`stroke()` 경로 렌더링에는 적용되지 않는다.

> 참고: 파이썬 렌더러(`poc/iso2.py`)는 PIL이 폴리곤을 안티앨리어싱하지 않아
> 이 문제가 없다. **브라우저 전용 보정이다.**

### 해결

렌더 후 blit 직전에 오프스크린 픽셀을 팔레트의 가장 가까운 색으로 스냅한다.

- `buildPalette()` — `style.json`의 색을 모으고 **처마 파생색**(`×0.72`, `×0.62`)도 포함한다.
  이 파생색을 빼면 처마가 엉뚱한 색으로 스냅된다
- `nearest()` — 15비트 RGB 키(`r>>3, g>>3, b>>3`)로 **32,768칸 LUT를 지연 캐싱**한다.
  캐시 없이 매 픽셀 57색과 거리 계산을 하면 프레임당 수백만 연산이 된다
- `quantize()` — `getImageData` → 치환 → `putImageData`
- **픽셀화를 끄면 양자화도 건너뛴다** (`PIX > 1`일 때만)

### 결과

| | 이전 | 이후 |
|---|---|---|
| 지도 영역 색 수 | 693 | **43** |
| 팔레트 정의 | — | 57색 |
| 전체 뷰 렌더 | 81ms | **102ms** |
| 확대 시 | 24~48ms | **31~79ms** |

양자화 비용은 **약 +20ms**다. 되돌리기 기준(줌 전환 1.5초)의 1/15이라 문제없다.
처음 150ms가 나온 것은 LUT warmup이었고 정상 상태는 위 수치다.

**경계에서 중간색이 완전히 사라졌다.** 확대해서 보면 계단이 또렷하다
(`docs/img/viewer-palette-gyeongbokgung.jpg`).

### 디더링은 넣지 않았다

계획서에는 "팔레트 제한 + 디더링"으로 적었으나 **디더링할 대상이 없다.**
모든 면이 단색 채우기라 계조가 존재하지 않는다. 디더링을 넣으면 의미 없는 노이즈만 생긴다.
벽면 질감은 **Phase 2-D 스프라이트**가 맡는 것이 맞다.

### 자체 검증 보강

`pixelCitySelfCheck()`에 팔레트 구성 확인과
"팔레트 색은 자기 자신으로 스냅된다" 검사를 추가했다.

## 2026-09-04 — Phase 2-E 검증: 랜드마크에 확산 모델이 필요 없다

### 국가유산청 API — 인증키 불필요

실제로 호출해 확인했다.

| 항목 | 내용 |
|---|---|
| 인증 | **없음.** 신청·키 불필요 |
| 제약 | **HTTPS 필수** (HTTP는 연결 자체가 안 된다) |
| 목록 | `https://www.khs.go.kr/cha/SearchKindOpenapiList.do?ccbaKdcd=&ccbaCtcd=&ccbaAsno=` |
| 이미지 | `https://www.khs.go.kr/cha/SearchImageOpenapi.do?...` → `imageUrl`·`imageNuri`·`ccimDesc` |
| 해상도 | 750×539 ~ **4000×2303** |

확보한 전각 코드 (`ccbaKdcd=11` 국보, `ccbaCtcd=11` 서울):

| 전각 | ccbaAsno | 이미지 |
|---|---|---|
| 경복궁 근정전 | `0002230000000` | 28장 (외관 A유형 15장) |
| 경복궁 경회루 | `0002240000000` | 27장 |
| 창덕궁 인정전 | `0002250000000` | 15장 |
| 창경궁 명정전 | `0002260000000` | — |
| 종묘 정전 | `0002270000000` | — |
| 서울 숭례문 | `0000010000000` | 28장 |

### 두 가지 발견 — 계획을 또 바꿔야 한다

**1. 스타일 변환에 AI가 필요 없다.**
사진을 축소하고 팔레트로 양자화하는 것만으로 근정전이 근정전으로 읽힌다.
96~128px가 적당하고 64px는 뭉개진다.
**디더링은 확실히 나쁘다** — 하늘에 체커보드 노이즈가 생긴다 (2-B의 판단과 일치).

**2. 시점 변환도 필요 없다.**
가장 큰 위험으로 잡았던 것이 "사진은 정면인데 우리는 아이소메트릭"이었다.
그런데 외관 사진 15장을 컨택트시트로 훑어보니 **3/4 부감으로 찍힌 사진이 실제로 있다**
(`경복궁 근정전`, 750×539). 지붕 두 겹과 측면이 동시에 보여 우리 투영에 가깝다.

→ **확산 모델(Qwen-Image-Edit 20B, 40GB 다운로드)이 불필요해졌다.**
   랜드마크는 사진 변환만으로 처리한다.

### 만든 것

`poc/landmark.py` — 국가유산청 사진 → 픽셀 스프라이트

- `images(key)` — 외관 후보만 추림. 세부 사진(내부·천장·현판·공포·잡상 등)과
  비안전 라이선스를 뺀다
- `cut_sky(im)` — **flood fill로 하늘 제거.** 단순 색 임계값으로 지우면 단청의 청색까지
  날아가므로 위 가장자리에서의 연결성을 본다
- `sprite(im, width)` — 축소 + 팔레트 양자화 (디더링 없음)

산출: `poc/sprites/geunjeongjeon_96.png` (96×67)

### 환경 확인

M3 Max / **128GB 통합 메모리** / MPS 사용 가능 / 디스크 3TB.
20B 확산 모델도 올릴 수는 있으나 **이번 발견으로 불필요해졌다.**
(참고: prototype2는 SDXL + ControlNet-canny 경로이고 캐시에 4.7GB 받아져 있다)

### 남은 다듬기

1. **처마 밑 하늘이 흰색으로 남는다** — flood fill이 처마 아래까지 닿지 못한다
2. **월대(바닥)가 스프라이트의 절반을 차지한다** — 건물 영역만 크롭해야 한다.
   지금은 하늘만 지우고 바닥은 그대로다
3. 지붕이 적갈색이다 — 원본 스캔 사진의 색이 그렇다(양자화 문제 아님). 색 보정 필요
4. 지도 축척에 맞춰 배치하는 작업 미착수

### ⚠️ 미해결 — 공공누리 유형

`imageNuri` 값이 **A / B / D**로 오는데 **A/B/C/D가 공공누리 몇 유형인지 공식 문서에 없다.**

A가 제3유형(변경금지)이면 픽셀아트 변환 자체가 위반이다.
1차 통과 시 대국민 공개검증 10일이 있어 여기서 걸리면 치명적이다.
