**A안(하이브리드) 채택.** 건물 기하는 공공데이터 그대로, AI는 스프라이트와 관광 기능에.

근거:
1. Phase 0 PoC에서 **AI 없이 비용 0으로 렌더가 나왔다** (`poc/poc_iso2.png`)
2. A안의 유일한 약점(궁궐이 상자로 나옴)이 **`strct_code_nm` 목구조 판별로 해소**됐다
3. 심사 배점상 정확성15 + 완성도20 + 수급성20 = **55점 구간에서 B안보다 유리**
4. D-14 안에 확실히 끝난다

B안(확산)은 **검증하지 않고 폐기**한다. 환각·이음새·검수 부담을 감당할 일정이 없다.
C안은 GeoAI 분야 정합성이 부족하다.

초기 기획([CONCEPT.md](CONCEPT.md))은 Isopolis 파이프라인(확산 모델 파인튜닝)을 기본값으로 깔고

**건물의 기하(모양·위치·높이)를 데이터에서 가져올 것인가, 모델에게 그리게 할 것인가.**

| 비용 | ~0 | $40~80 + GPU 시간 |

| 재현성 | API 키만 있으면 됨 | GPU·학습 필요 |

## 2. 후보 3안

### A안 — 하이브리드 (기하는 데이터, 스타일은 AI)

건물 형상·위치·높이는 공공데이터로 정확히 렌더하고,
그 위에 얹을 **지붕·외관 스프라이트를 건물 용도별로 AI 생성**한다.

```
건물 형상/위치/높이 ← 국토부 GIS건물통합정보 / V-World 3D (정확)
건물 표면 스타일    ← AI 생성 픽셀 스프라이트셋 (용도 속성으로 자동 매핑)
지형/도로/물        ← 벡터 (정확)
랜드마크 (경복궁 등) ← 수제 스프라이트 또는 AI + 수작업
관광 코스/질의      ← AI
```

- 학습량: 건물 용도별 스프라이트 **수십 종** (타일 1,500샘플 학습 ✕)
- 검수: 스프라이트만 보면 됨 (사분면 160개 육안 검수 ✕)
- **환각·이음새·물 오인식 문제가 구조적으로 발생하지 않음**
- 진짜 픽셀아트로 나옴 — HN이 Isopolis를 깐 "흐릿함·흔들리는 선" 문제 없음

### B안 — 확산 모델 파인튜닝 (Isopolis 원안)

3D 렌더 → LoRA 학습 → 슬라이딩 윈도우로 타일 생성 → 육안 검수.

- 혁신성 점수는 최상
- 대신 [RESEARCH-isopolis.md](RESEARCH-isopolis.md)의 문제를 그대로 상속:
  환각, 이음새 불연속(미해결), 물 오인식, 수동 검수
- D-16에 위험. 비용 $40~80

### C안 — AI 없이 결정론적 렌더

지도는 순수 벡터 렌더. AI는 관광 코스 생성·자연어 질의 등 **기능**에만.

- 가장 빠르고 안전, 비용 ~0, 정확성 만점
- **분야가 "GeoAI 혁신 아이디어"인데 지도 생성에 AI가 없다** → 혁신성 15점 약함

## 4. 데이터 확인 결과

### ✅ 확인됨

| 데이터 | 출처 | 내용 |
|---|---|---|
| **건물 폴리곤 + 층수 + 높이 + 용도** | **국토부 GIS건물통합정보** (공공데이터포털, SHP) | 수치지형도 건물 레이어 + 건축물대장(세움터) 속성 통합 |
| 같은 데이터 API판 | 국토부 용도별건물정보 (WMS/WFS/속성정보) | data.go.kr |
| 3D 건물 모델 | V-World 3D 데이터 API | LOD1 전국 / **LOD3~4 주요 도심**. gltf·glb·collada·obj·dae·3ds |
| 항공영상 | V-World | 25cm |
| DEM | V-World | 5m |
| 도로·하천·경계 벡터 | V-World WFS `api.vworld.kr/req/wfs` | 엔드포인트 확인 |

**압출에 필요한 층수·높이 속성이 붙어 있다는 점이 핵심이다.**
폴리곤을 높이만큼 세우고 아이소메트릭 직교 투영 → 팔레트 제한 + 픽셀 그리드 스냅 = 픽셀아트.
V-World 3D 모델(LOD1~4)은 이미 벡터 지오메트리라 압출 없이 그대로 렌더해도 된다.

## 5. 알려진 한계 — 압출 방식

**압출은 "상자"다.** 폴리곤을 높이만큼 세운 것이라 지붕 형태·창문·디테일이 없다.

| 대상 | 압출 결과 | 대응 |
|---|---|---|
| **경복궁 기와지붕** | 납작한 상자. 전혀 안 나옴 | 수제 스프라이트 또는 AI 생성 |
| **북촌 한옥** | 작은 상자 밭 | 한옥 전용 스프라이트셋 |
| 남산서울타워 | 원통 상자 | 수제 |
| 일반 아파트·오피스 | **오히려 잘 맞음** (실제로 상자라서) | 용도별 스프라이트 |

→ **이 한계가 A안에서 AI가 들어갈 자리를 정확히 규정한다.**
건물 용도 속성이 데이터에 이미 있으므로 스프라이트 매핑은 자동화된다.

### A안에서 AI가 담당하는 것

기하에서 손을 떼는 대신, AI는 **보이는 방식**과 **안내하는 방식**을 맡는다.

1. **건물 표면 스프라이트 생성** — 용도별 창문·기와·간판 픽셀 타일셋 (수십 종)
2. **관광 코스 생성** — POI + 보행경로 + 혼잡도 조합
3. **자연어 공간 질의** — "한옥 보러 갈 만한 곳" → 지도 반응

전부 **환각해도 지도의 좌표 정확성을 훼손하지 않는 자리**다. 이게 A안의 핵심 설계다.

## 7. 뷰어 렌더 방식 — ② 브라우저 직접 렌더 채택 (2026-09-04)

A안으로 지도를 만들기로 한 뒤, **그 지도를 화면에 어떻게 띄울지**가 다시 갈렸다.

| | ① 사전 렌더 PNG | ② 브라우저 직접 렌더 |
|---|---|---|
| 파이썬이 하는 일 | PNG를 미리 그림 | 폴리곤을 JSON으로 내보냄 |
| 브라우저가 하는 일 | 이미지 팬·줌 | 매번 건물을 그림 |
| 줌 | 이산적 (1x/2x/4x) | 단계별이되 재렌더 |
| 상호작용 | 화면 좌표 JSON으로 하이테스트 | 폴리곤 직접 판정 |
| 위험 | 없음 (렌더러 1벌) | **투영 로직이 두 벌** |

**② 채택.** 상호작용이 자연스럽고 확대해도 도형이 깨지지 않는다.
감수한 것은 **렌더러 이중화**다 — `poc/iso2.py`와 `web/app.js`가 같은 투영을 각각 구현한다.

### 이중화 방어 장치

1. **`poc/style.json` 단일 상수원** — 팔레트·방위각·고도각·층고·처마 배율을 한 파일에 두고
   파이썬과 JS가 같은 것을 읽는다. 색을 바꿔도 한 곳만 고친다.
2. **골든 값 대조** — `export.py`가 파이썬 `proj()` 결과 5건을 `meta.json`에 넣고,
   `app.js`가 로드 시 자기 계산과 대조해 어긋나면 콘솔에 오류를 찍는다.
   **포팅 버그를 조용히 넘기지 않기 위한 장치다.**

### ②→① 되돌리기 기준 (미리 정해뒀다)

"조금만 더 고치면 된다"로 시간을 태우지 않기 위해 선을 그었다. 하나라도 걸리면 ①로 되돌린다.

| 시점 | 조건 | 실측 |
|---|---|---|
| 골든 값 대조 후 | 투영 불일치를 2시간 내 못 잡으면 | **5건 일치, 재작업 0회** |
| 첫 전체 렌더 후 | 줌 전환 1.5초 이상 | **6,991동 전체 112ms** |
| 09-08 | 팬·줌·클릭 셋 다 안 되면 | **09-04에 셋 다 동작** |

**세 기준 모두 여유 있게 통과했다. ②를 유지한다.**

되돌리기 비용이 낮다는 점이 애초 결정의 근거였다 — `iso2.py`가 이미 PNG를 만들고 있고
`export.py`의 좌표 계산은 ①에서도 그대로 쓰인다. 버려지는 작업이 없는 구조로 짰다.
