# Phase 0 PoC — V-World WFS 압출 렌더

V-World WFS에서 받은 **건물 폴리곤 + 지상층수**만으로 아이소메트릭 픽셀 렌더가
가능한지 검증한 코드. **AI 없음, 비용 0.**

## 실행

```bash
export VWORLD_API_KEY=...        # vworld.kr 오픈API 인증키
export VWORLD_API_DOMAIN=...     # 인증키에 등록한 도메인

# 데이터 받기 (경복궁~삼청동 일대)
BBOX="126.9740,37.5760,126.9820,37.5820"
for L in lt_c_spbd lt_l_sprd lt_c_uo301; do
  curl -s -o "gf_${L}.json" \
    "https://api.vworld.kr/req/wfs?SERVICE=WFS&REQUEST=GetFeature&VERSION=2.0.0&TYPENAME=${L}&BBOX=${BBOX}&SRSNAME=EPSG:4326&OUTPUT=application/json&MAXFEATURES=1000&KEY=${VWORLD_API_KEY}&DOMAIN=${VWORLD_API_DOMAIN}"
done
mv gf_lt_c_spbd.json gf_bld.json

pip install Pillow
python iso.py                    # -> poc_iso.png
```

## 사용 레이어

| 레이어 | 내용 | 쓰는 필드 |
|---|---|---|
| `lt_c_spbd` | 도로명주소건물 | `gro_flo_co` 지상층수, `buld_nm` 건물명, 폴리곤 |
| `lt_l_sprd` | 도로명주소도로 | 라인, `road_bt` 도로폭 |
| `lt_c_uo301` | 국가유산 지정/보호구역 | 폴리곤 (경복궁 등) |

## 결과

`poc_iso.png` — 292동, 최고 6층, scale 1.84 m/px.

## 알려진 한계

- **실측 높이 없음.** `gro_flo_co`(층수) × 3m로 추정 (`FLOOR_H`)
- **용도 구분 불가.** `buld_se_cd` 전부 `'0'`, `poi_chk` 전부 `null`
  → 용도별 스타일링하려면 국토부 GIS건물통합정보 필요
- **지붕 형태 없음.** 궁궐 전각·한옥이 납작한 상자로 나옴 → 스프라이트로 보강해야 함
- WFS는 bbox에 걸친 피처 **전체**를 반환한다. 프레임은 bbox로 고정한다 (`BBOX` 상수)

# v2 — 용도별건물정보(dt_d198) 단독 렌더  ← **이쪽이 본선**

`iso2.py` / `poc_iso2.png`.

V-World **디지털트윈국토(dtna) API**는 기존 오픈API(`/req/wfs`)와 **다른 카탈로그**다.

`lt_c_spbd`와 조인할 필요가 없다.

## 엔드포인트

```bash
# 대량 조회 (bbox) — 이걸 쓴다
https://api.vworld.kr/ned/wfs/getBuildingUseWFS?typename=dt_d198&bbox=<minx,miny,maxx,maxy>&srsname=EPSG:4326&maxFeatures=1000&key=<KEY>&domain=<DOMAIN>

# 건물연령 (동일 방식, typename 다름)
https://api.vworld.kr/ned/wfs/getBuildingAgeWFS?typename=dt_d196&...

# 단건 조회 (PNU) — buldHg(실측 높이)는 여기에만 있다
https://api.vworld.kr/ned/data/getBuildingUse?pnu=<19자리>&format=json&key=<KEY>&domain=<DOMAIN>
```

> ⚠️ **필드명 표기가 다르다.** WFS는 snake_case(`buld_prpos_cl_code_nm`),
> 데이터API는 camelCase(`buldPrposClCodeNm`).

# DEM 지형 — `terrain.py`

공개DEM(도엽 37608, 90m, EPSG:5179)을 **우리 ENU 프레임 위 정규격자로 리샘플**해
`web/data/terrain.json`을 만든다. 뷰어와 `iso2.py`가 둘 다 이 파일을 읽는다.

## 실행

```bash
# 원본은 사용자 Google Drive: projects/공간정보_Vworld/dataset/
DEM=".../(B080)공개DEM_37608_img_2025/37608/37608.img"
uv run --with rasterio python terrain.py "$DEM" --check   # 검증만
uv run --with rasterio python terrain.py "$DEM"           # terrain.json 생성
```

`terrain.json`은 10.8KB로 **커밋돼 있다.** 보통은 다시 만들 필요가 없고,
원본 `.img`가 없는 환경에서도 뷰어가 그대로 돈다.

## 산출물

```
격자 47x60 = 2,820점 / step 90m / pad 900m
datum z0 26.8m (ENU 원점 = bbox 중심의 표고) / 상대고도 -10.1 ~ 259.7m
음영 셀 1,045개 (2,714칸 중 기복 있는 것만 — 나머지는 평지색으로 남는다)
```

## 왜 이런 구조인가

- **ENU는 lon/lat의 선형 사상**이라(`e=(lon-lon0)*mlon`) ENU 정규격자 = EPSG:4326
  축정렬 격자다. `rasterio.warp.reproject` 한 호출로 CRS 변환·보간·nodata가 끝난다.
- **프레임은 `web/data/meta.json`에서 읽는다.** `export.py`를 import하면 PIL 연쇄로
  죽고, `origin()`을 복붙하면 프레임이 분기한다.
- **패드 900m가 필수다.** 남산 정상이 프레임 남쪽 경계에서 안쪽 **22m**밖에 안 들어와
  패드 없이는 정상이 격자 끝 절벽에 걸린다.
- **과장(`exag`)은 값에 굽지 않는다.** 교정은 `terrain.json`의 숫자 하나만 고치고
  새로고침 — 원본 `.img`가 다시 필요하지 않다.
- **음영은 표고 밴드가 주 신호다.** 경사만 쓰면 균일 사면이 균일 톤이 되어 산이 평지와
  같은 색이 된다 (실측: 남산 종단면 232m→31m에서 단계 2개만 쓰이고 휘도가 평지와 동일).
  `단계 = neutral + round(표고/zband) - round(경사*gain)`, 8단 램프.
- **램프는 채널별 배율**이라 위로 갈수록 밝아지며 난색으로 간다 (초록→황록).
  휘도만 올리는 것보다 눈에 띄고 `heri` 녹색 채널의 255 클리핑도 피한다.

## 공유 함수 (렌더러 이중화 방어)

| 함수 | JS 대응 | 검증 |
|---|---|---|
| `zq(g, e, n)` | `app.js zAt()` | 184점 최대오차 2.8e-14 |
| `cells(g, zones)` | `app.js buildTerrainCells()` | 1,045셀 전부 동일 |

`iso2.py`가 이 둘을 import해 재사용하므로 파이썬 구현은 하나다.
`terrain.json`의 `golden` 3건은 JS가 로드 시 대조한다.

## 알려진 한계

- **90m 격자** — 청계천 저지대·종로 능선 같은 도심 미세 기복은 못 잡는다
- **인왕산 46m / 북악산 129m** (실제 338m/342m) — 원본 결함. 둘 다 현재 bbox 밖이라

## 왜 지붕과 벽을 분리하나

묶어두면 (용도 × 재질 × 연령)마다 3색이 필요해 **630색**이 든다. 분리하면

# 실측 층고 보정 — `buld_hg`

높이를 **층수 × 상수**로 추정하던 것을 실측 기반으로 바꿨다. 상수가 계통적으로 틀렸었다.

| | 옛 상수 | 실측 중앙 | 오차 |
|---|---|---|---|
| 일반 | 3.0 m/층 | **3.48** | +16% |
| 한옥 | 5.0 m/층 | **4.00** | −20% |
| 궁궐 | 7.0 m/층 (`wood_floor_h × palace_scale`) | **8.25** | +18% |

**결과: 높이 총합 +12.1%.** 일반 평균 13.3→15.9m, 한옥 6.5→5.2m, 최고 건물 111→**160.2m**.

## 규칙

```
buld_hg > 0 이고 높이/층수 >= hg_min_ratio  ->  실측을 그대로 (36.3%)
아니면                                    ->  층수 × floor_h_curve
```

`floor_h_curve`는 실측 2,545동의 **층수별 중앙값**이다. 손으로 정한 상수가 아니다.

```
1층 4.60 · 2층 3.70 · 3층 3.40 · 4~6층 3.30 · 7~9층 3.40 · 10~13층 3.70 · 14층+ 4.00
```

U자형이다 — 저층은 1층 상가 층고가 높고 고층은 로비·기계층이 높다. 계단 표이고 보간하지 않는다.

## 이상치 가드는 **비대칭**이다

| 증상 | 건수 | 무엇이 틀렸나 | 처리 |
|---|---|---|---|
| 층고 > 8m | 12동 | **층수 기록** (D동 1층 47.4m, 창덕궁 인정전 1층 21.0m) | **실측 유지** — 자르면 옳은 값을 잃는다 |
| 층고 < 2.0m | 6동 | **높이 기록** (안국빌딩 15층 12.5m) | 곡선으로 폴백 |

## ⚠️ 궁궐 대전은 이걸로 안 고쳐진다

경복궁 주요 전각(근정전·경회루·사정전·수정전·흥례문)은 **`buld_hg`가 전부 없다.**
폴백 8.25m를 타는데 실제 근정전은 약 25m다. 건축면적 회귀는 n=11·r=0.62로 약해
(인정전 예측 13.0m vs 실측 21.0m) 넣지 않았다. **궁궐 대전은 2-E 랜드마크 스프라이트의 몫이다.**

서울타워도 `buld_hg`가 0이고 8층으로 기록돼 24m로 그려진다 (실제 236m). 데이터 한계다.

## 되돌리기

`floor_h_curve`를 지우면 `floor_h`/`wood_floor_h` 상수로, `hg_min_ratio`를 999로 두면
실측을 전부 무시하고 곡선만 쓴다. 두 축이 독립이다.

# 지붕색 — V-World 정사영상 실측 (`roofcolor.py`)

지붕색이 주용도로만 갈리는데 **주용도는 공간적으로 군집한다** — 근생은 근생끼리,
주택은 주택끼리 붙어 있다. 그래서 조합이 102종이어도 화면에서는 덩어리로 보였다
(최근접 이웃과 지붕색이 사실상 같은 건물 **43.5%**). 영상에서 실제 색을 가져와 깬다.

```
export VWORLD_API_KEY=...
uv run --with pillow python roofcolor.py --selfcheck   # 코드만 검사
uv run --with pillow python roofcolor.py --stats       # 표본 통계만, 파일 안 씀
uv run --with pillow python roofcolor.py               # -> cache_roof.json
python3 export.py                                      # -> web/data/city.json 에 반영
```

**3D가 아니라 2차원 항공영상이다.** V-World 3D DATA API는 중단됐고 3차원 데이터는
국가공간정보 보안관리규정상 '공개제한'이라 복제·출력이 불가하다 — 뷰어를 화면 캡처하는
것도 같은 제한을 받는다. 정사영상은 별개 데이터셋이고 WMTS로 공개돼 있다.

```
https://api.vworld.kr/req/wmts/1.0.0/{KEY}/Satellite/{z}/{y}/{x}.jpeg
⚠️ 경로 순서가 {z}/{y}/{x}다. x/y를 바꾸면 "서비스 제공영역이 아닙니다"
⚠️ 영상은 Satellite뿐이다. Base는 같은 좌표에서 404
z18 = 0.473 m/px · bbox 전체 600타일 · 8.2MB · 약 2.5분
```

## 왜 되는가 — 기울어짐이 작다

정사영상은 **지형만** 정사보정한다. 건물은 천저점에서 방사상으로 기울어져 벽이 찍히고,
그게 지붕 샘플링에는 오차다. 그런데 **서울 도심 건물의 90%가 20m 이하**라
수평 변위가 1.5m 이하 = z18에서 3.2화소다. 침식 몇 화소로 흡수된다.

침식 반경 = `0.078 × 높이 / (m/px)`, 최소 1화소. 남은 화소가 `ortho_min_px` 미만이면
표본 실패로 보고 **오늘 색으로 폴백**한다. 실측 성공률 **97.2%** (폴백 2.8%).

## 명도만 올리고 채도는 안 올린다

영상의 지붕은 어둡다(명도 중앙 94, 규칙색은 171). 좁은 골목 건물은 지붕이 그림자에
들어가 표본이 실제보다 어둡다. `ortho_lift`의 명도 보정이 그 보정이기도 하다.

⚠️ **채도는 실측으로 반증됐다.** 1.45배 하면 이웃 동일색이 15.9% → **17.7%로 나빠진다** —
색상이 비슷한 것끼리 채도를 올리면 서로 더 가까워진다. 화면으로도 형광 연두가 튄다.

## 한옥은 태우고 궁궐은 뺀다

한옥 2,352동은 실측을 타고(`ortho_hanok`) **궁궐 전각 98동은 스위치와 무관하게 제외**한다
— 랜드마크라 기와색이 정체성이고 표본이 나무 그늘에 오염된다.
**처마 파생색(×0.72/×0.62)은 기존 기와에서 나온 것을 그대로 쓴다** — 실측 12색마다
파생 2개를 구우면 +24색이라 예산 160을 넘는다. 팔레트 추가 0색.

## 되돌리기 — 세 층

```
실측 ON                    이웃 동일색 16.3%   팔레트 149색
ortho_hanok: false                    29.5%          (한옥만 기와색으로)
cache_roof.json 삭제                  43.5%   팔레트 137색   <- 원래 값
```

1. `cache_roof.json` 삭제 → `export.py`가 `roofc`/`roof_rgb`를 안 내보내고 양쪽 다 오늘 색
2. `style.json`의 `roof_ortho: false` → 파일을 둔 채 끈다
3. `ortho_hanok: false` → 한옥만 기와색으로

`zoom`/`k`/`min_px`/`lift`는 **재생성 파라미터**다. 바꾸면 `roofcolor.py`를 다시 돌려야
한다 — 보정은 중심 색에 이미 구워져 있고 런타임에는 아무 계산도 안 한다.

# 건물 파사드 (세로 리브 · 창문)

벽의 세로 구조. **뷰어 전용이다** — `iso2.py`는 고정 축척에서 칸이 0.76~2.37px라
게이트(2.5px) 아래로 떨어져 미러링하지 않았다. 근거는 `docs/APPROACH.md §7`.

```
칸 폭 = facade_bay[주용도](m) x 면 방향의 화면 단축 / (m per artpx)
  < facade_min_px         ->  안 그린다
  facade_min_px ~ win_px  ->  세로 리브, facade_rib_every 베이마다
  >= facade_win_px        ->  창문 칸 (단, 층 띠가 층마다 있을 때만)
```

**단축이 0.50~1.00배로 갈리므로 등급은 건물이 아니라 면마다 정해진다.** 같은 건물에서
정면은 창문, 급단축된 면은 리브가 되는 게 정상이다.

**잉크는 반대 면의 색이다** — 밝은 면엔 `dark`, 어두운 면엔 `lit`. 둘 다 이미 팔레트에
있어 **새 색이 0개**고, 어두운 면이 비어 있던 문제도 이걸로 메운다.

창을 그리는 면에는 **층 띠를 그리지 않는다.** `sy()`의 ±1px 반올림 지터로 가로선이
물결치는데 반듯한 창과 겹치면 지저분하다. 창이 이미 층을 표현하므로 중복이기도 하다.

근생(`facade_shop`)은 `fl >= 2`면 맨 아래 층을 건너뛴다 — 1층은 상가라 파사드가 다르다.
목조(`kind != 0`)는 제외한다. 한옥 창살은 격자가 달라 2-C·2-E의 몫이다.
