## 1. 왜 별도 프로토타입인가

기존 `poc/`와 `web/`은 공간 정확성과 데이터 레이어 결합에는 성공했다. 그러나 결과는
"픽셀로 표시한 GIS 압출 렌더"에 가깝고, 참고 픽셀 지도의 일러스트적인 느낌과 차이가 크다.

부족한 부분은 단순히 해상도나 팔레트만의 문제가 아니다.

- 지붕·창문·간판·수목·차량·보도 등 장면을 채우는 디테일이 적다.
- 건물이 실제 footprint를 그대로 올린 상자여서 실루엣 변화가 부족하다.
- 모든 객체가 하나의 조명·색감·묘사 밀도로 통합되어 보이지 않는다.
- 경복궁·한옥 등 서울의 정체성을 만드는 대상이 일반 건물과 충분히 구별되지 않는다.
- POI와 공간정보는 풍부하지만, 배경 지도가 탐험하고 싶은 일러스트로 보이지 않는다.

`prototype2`에서는 기존 구현을 수정하거나 폐기하지 않는다. 기존 렌더를 정답 좌표가 담긴
가이드로 활용하고, 이미지 모델이 그 위에 시각적 해석을 추가하는 별도 경로를 시험한다.

## 2. 핵심 가설

```text
공간데이터
  ├─ 기본 RGB 렌더
  ├─ 건물·도로 윤곽선
  ├─ 높이/깊이 맵
  └─ 의미 마스크(궁궐·한옥·상업·주거·공원)
               ↓
        이미지 편집 모델
               ↓
   아이소메트릭 픽셀 일러스트
               ↓
 실제 좌표의 POI·지하철·관광 경로 재결합
```

검증할 가설은 다음과 같다.

1. 모델이 도로망과 주요 건물 배치를 알아볼 수 있을 만큼 유지할 수 있다.
2. 절차적 렌더보다 참고작에 가까운 색감·질감·장면 밀도를 만들 수 있다.
3. 같은 설정을 인접 구간에 적용했을 때 스타일 차이를 관리할 수 있다.
4. 공간 정확성은 배경 이미지와 데이터 오버레이를 분리함으로써 설명할 수 있다.

## 3. 이번 실험에서 하지 않는 것

- 시작부터 서울 도심 전체를 생성하지 않는다.
- 모델 하나를 미리 확정하지 않는다.
- 첫 단계부터 LoRA를 학습하지 않는다.
- 기존 `poc/`, `web/` 파일을 덮어쓰지 않는다.
- 생성 결과를 좌표·면적·높이가 정확한 원천 데이터라고 주장하지 않는다.
- API 서비스 약관을 확인하지 않은 출력물을 학습 데이터로 사용하지 않는다.
- 참고작의 이미지를 학습 데이터나 직접적인 스타일 복제 대상으로 사용하지 않는다.

## 4. 성공 기준

대표 구간 한 장에서 아래 항목을 평가한다. 각 항목은 1~5점으로 기록한다.

| 평가 항목 | 통과 기준 | 확인 방법 |
|---|---:|---|
| 시각적 매력 | 4점 이상 | 기존 렌더와 나란히 놓고 사람이 평가 |
| 픽셀아트 일관성 | 4점 이상 | 픽셀 크기·윤곽선·팔레트·명암 방향 확인 |
| 도로 구조 보존 | 4점 이상 | 원본 윤곽선과 반투명 중첩 비교 |
| 랜드마크 식별성 | 3점 이상 | 경복궁 주요 전각·광장 위치 육안 대조 |
| 환각 억제 | 3점 이상 | 건물 추가·삭제, 가짜 수면·도로 집계 |
| 재현성 | 동일 설정 3회 중 2회 이상 사용 가능 | seed를 달리해 반복 생성 |
| 제작 시간 | 대표 구간 1일 이내 | 입력 준비부터 후보 선정까지 기록 |

다음 중 하나라도 발생하면 전체 구역 확대를 보류한다.

- 주요 도로가 끊기거나 방향이 바뀐다.
- 경복궁 영역에 대형 건물이 임의로 추가·삭제된다.
- 같은 프롬프트와 조건으로도 스타일 편차가 지나치게 크다.
- 한 구간을 고르는 데 수십 회 이상의 생성과 장시간 수동 보정이 필요하다.
- 출력물 사용 및 후속 학습 권리를 명확히 설명할 수 없다.

## 5. 디렉터리 계획

구현을 시작하면 다음 구조를 사용한다. 생성물과 원본 조건 이미지를 섞지 않는다.

```text
prototype2/
├── README.md               # 이 문서
├── configs/                # 모델·프롬프트·seed·강도 설정
├── scripts/                # 조건 이미지 생성, 추론, 비교 리포트
├── inputs/
│   ├── source/             # 기존 렌더에서 가져온 대표 구간
│   └── conditions/         # edge/depth/semantic mask
├── outputs/
│   ├── candidates/         # 모델 원본 출력
│   └── selected/           # 사람이 채택한 결과
├── eval/                   # 평가표, 오버레이, 실패 사례
└── LICENSES.md             # 모델·가중치·데이터·출력 이용조건 기록
```

대용량 모델 가중치와 캐시는 저장소에 넣지 않는다. 실제 디렉터리를 만들 때 `.gitignore`를
먼저 확인하고 필요한 패턴만 추가한다.

## 6. 상세 진행 단계

### P2-0. 기준선 고정

목적은 무엇이 좋아졌는지 비교할 기준을 만드는 것이다.

- [x] 대표 구간을 **경복궁 중심 1개**로 고정한다.
- [x] 비교용 기존 렌더 PNG와 동일 범위의 좌표 bbox를 기록한다.
- [x] 출력 해상도, 방위각, 고도각, 축척을 고정한다.
- [ ] 기존 렌더의 장점과 단점을 스크린샷에 주석으로 남긴다.
- [ ] 참고작에서 원하는 특성을 문장으로 분해한다.
  - 제한된 팔레트
  - 강한 지붕/벽 명암
  - 작은 창문과 수목의 반복 리듬
  - 거리·마당·보도의 생활 디테일
  - 랜드마크의 제한적 과장
- [ ] 비교 기준 이미지는 출처와 이용 범위를 기록하고, 학습 입력으로 사용하지 않는다.

**산출물:** 기준 PNG, bbox/카메라 설정 JSON, 기준선 평가표.

### P2-1. 조건 이미지 생성

기존 공간데이터에서 이미지 모델의 구조 보존에 필요한 채널을 만든다.

- [x] `RGB base`: 현재 팔레트로 렌더한 기본 아이소메트릭 장면.
- [x] `edge`: 건물 외곽, 도로 경계, 궁궐 담장 등을 단색 선으로 출력.
- [x] `height/depth`: 건물 높이와 지형 고도를 명암으로 표현.
- [x] `semantic mask`: 색상 ID로 클래스를 구분.
  - 궁궐 전각
  - 일반 한옥/목구조
  - 상업용
  - 주거용
  - 문교사회용
  - 도로/보도
  - 공원/녹지
  - 물
- [x] 모든 조건 이미지가 같은 크기와 픽셀 좌표를 사용하는지 자동 검사한다.
- [x] 지도 외곽의 빈 영역은 명확한 마스크 값으로 통일한다.

**산출물:** 동일 해상도의 RGB·edge·depth·semantic PNG 세트와 생성 스크립트.

### P2-2. 모델 및 라이선스 후보 확정

최소 2개 경로를 비교하되, 설치와 비용 때문에 후보를 무한히 늘리지 않는다.

- [ ] 후보 C(선택): FLUX.1-schnell — 개별 스프라이트 또는 스타일 탐색용.
- [ ] 각 후보에 대해 다음을 `LICENSES.md`에 기록한다.

- [ ] GPU 메모리 요구량, 예상 실행 시간, 예상 비용을 기록한다.

**판정:** 품질뿐 아니라 공개검증에서 설명 가능한 후보만 다음 단계로 보낸다.

### P2-3. 프롬프트만으로 1차 변환

LoRA 없이 모델 자체의 구조 보존 능력과 스타일 적합성을 먼저 본다.

- [ ] 공통 프롬프트와 금지 프롬프트를 작성한다.
- [ ] 아이소메트릭 시점, 픽셀 크기, 팔레트, 조명 방향을 명시한다.
- [ ] 도로·건물 배치를 바꾸지 말라는 구조 보존 지시를 포함한다.
- [ ] 모델별 권장 입력 방식에 맞춰 RGB/edge/depth 조건을 적용한다.
- [ ] 조건 강도 또는 denoise strength를 낮음·중간·높음 3단계로 비교한다.
- [ ] 설정별 seed 3개만 생성해 탐색량을 제한한다.
- [ ] 프롬프트·seed·모델·샘플러·스텝·조건 강도를 결과 파일과 함께 저장한다.
- [ ] 기존 렌더와 결과를 나란히 비교하는 contact sheet를 만든다.

**핵심 질문:** "멋있지만 다른 도시"가 아니라 "같은 장소를 더 매력적으로 그린 지도"인가?

### P2-5. 인접 타일 연속성 실험

대표 구간에 성공한 뒤에만 타일 문제를 확인한다.

- [ ] 서로 25~50% 겹치는 인접 구간 2~4장을 만든다.
- [ ] 동일 모델·프롬프트·팔레트·seed 정책으로 생성한다.
- [ ] 중첩 영역에서 도로·건물·색감 차이를 시각화한다.
- [ ] 독립 생성, 이전 타일을 문맥으로 제공, 겹침 후 중앙부 크롭 방식을 비교한다.
- [ ] 단순 블렌딩으로 해결할 수 없는 기하 충돌을 별도 집계한다.
- [ ] 가장 단순하게 반복 가능한 생성 순서를 확정한다.

**결정 게이트 2:** 인접 타일 4장으로 2×2 장면을 만들었을 때 이음새가 탐색을 방해하지 않아야 한다.

### P2-6. LoRA 필요성 판정

LoRA는 기본 전제가 아니라 다음 문제가 실제로 확인될 때만 도입한다.

- 타일마다 팔레트와 조명이 크게 달라진다.
- 서울 건축 요소가 반복해서 일반적인 서양식 건물로 변한다.
- 프롬프트가 길어져도 지붕·창문·수목 표현이 안정되지 않는다.
- 같은 구조 조건에 대해 원하는 표현을 반복 재현하지 못한다.

도입한다면:

- [ ] 학습 목적을 **스타일 일관성**으로 제한한다. 공간 좌표 학습을 기대하지 않는다.
- [ ] 학습 이미지의 생성·이용·재학습 권리를 전부 확인한다.
- [ ] 입력/정답 쌍을 버전 관리 가능한 목록으로 기록한다.
- [ ] 적은 수의 고품질 샘플로 시험하고, 처음부터 100쌍을 만들지 않는다.
- [ ] LoRA 없음/있음 결과를 동일 조건에서 비교한다.
- [ ] 개선 폭이 작으면 즉시 LoRA를 폐기한다.

**산출물:** LoRA 채택/폐기 결정 기록. 채택 시 가중치, 학습 설정, 데이터 명세.

### P2-7. 좌표 레이어 재결합

생성된 배경은 일러스트이며, 인터랙티브 정보는 원본 좌표를 유지한다.

- [ ] 기존 `web/data/` 좌표를 동일 카메라 투영으로 변환한다.
- [ ] 관광 POI, 지하철역, 경로를 생성 배경 위에 별도 Canvas/UI 레이어로 표시한다.
- [ ] 생성 과정에서 이동한 시각적 건물과 POI 마커가 심하게 어긋나는지 확인한다.
- [ ] 마커가 배경을 과도하게 가리지 않도록 줌별 밀도를 조정한다.
- [ ] 배경 이미지와 데이터 레이어의 정확성 범위를 UI 또는 제출 문서에 구분해 설명한다.

### P2-8. 제한 범위 확대

- [ ] 먼저 경복궁~광화문 약 2km²만 생성한다.
- [ ] 생성 시간·비용·실패율·수동 검수 시간을 실측한다.
- [ ] 실측치를 이용해 전체 7.86km² 확대 비용을 다시 계산한다.
- [ ] 마감 전에 전체 범위가 안전한 경우에만 확대한다.
- [ ] 생성 원본, 선택본, 재생성 사유를 추적 가능하게 남긴다.

### P2-9. 제출 증빙 정리

- [ ] 데이터 → 조건 이미지 → 모델 출력 → 좌표 레이어의 흐름도를 만든다.
- [ ] 기존 렌더와 prototype2 결과의 동일 구간 비교 이미지를 만든다.
- [ ] 사용한 공공데이터·모델·라이선스·출처 표시를 정리한다.
- [ ] AI가 바꿀 수 있는 부분과 정확히 유지되는 부분을 명시한다.
- [ ] 환각 검수 방법과 발견된 한계를 숨기지 않고 기록한다.
- [ ] 프로토타입 URL 또는 실행 화면을 제출 문서에 넣는다.

## 8. 최종 선택지

실험 결과에 따라 다음 중 하나를 명시적으로 선택한다.

1. **prototype2 채택:** 구조 보존과 미감이 모두 통과. 생성 배경 + 실제 좌표 레이어로 전환.
2. **부분 채택:** 전체 배경은 기존 렌더를 쓰고, 궁궐·한옥·수목 등 일부 에셋만 AI 결과를 사용.
3. **단일 장면 채택:** 연속 타일은 실패했지만 대표 구간 품질은 좋음. 공모전 데모 범위를 축소.
4. **폐기:** 미감 개선보다 환각·이음새·검수 비용이 큼. 기존 프로토타입을 제출 기반으로 유지.

어떤 결론이 나와도 기존 작동 프로토타입은 보존한다. `prototype2`의 성공 기준은 AI를 썼다는
사실이 아니라, **참고 픽셀 지도에 가까운 경험을 마감 안에 재현하면서 공간데이터 기반이라는
설명을 유지할 수 있는가**이다.
